# Серверы в Uztelecom Cloud

План переезда — в [docs/backlog.md](../docs/backlog.md), раздел 2. Здесь —
как устроены и как выкладываются **тестовый сервер** `staging.savdex.uz`
и **боевые машины** (сайт; админка и фоновые задачи; база) — раздел
[«Боевые машины»](#боевые-машины).

## Как код попадает на сайт

1. **Проверка «CI»** ([.github/workflows/ci.yml](../.github/workflows/ci.yml))
   — на каждый коммит каждой ветки: разбор кода и типы, тесты в четыре
   потока ([python.yml](../.github/workflows/python.yml)), сборка образа и
   прогон внутри него ([docker.yml](../.github/workflows/docker.yml)),
   типы фронтенда. Если ветка меняет только документацию (`docs/`,
   `*.md`), тяжёлые части пропускаются. Итог — одна проверка «CI»:
   зелёная, только когда всё нужное прошло.
2. **Слияние** в основную ветку — только через PR и только при зелёной
   «CI» на ветке, обновлённой до основной (правило ветки, ниже).
3. **Тестовый сервер** — каждый коммит основной ветки, но только после
   зелёной «CI» на нём; затем проверка снаружи. Прошла — коммит
   становится **кандидатом в релиз** (раздел «Выкладка»).
4. **Боевые машины** — релизом по кнопке («Боевые машины → Выкладка»).

### Правило основной ветки (один раз, в GitHub)

Settings → Rules → Rulesets → New ruleset → New branch ruleset:

- Ruleset name — `основная ветка`, Enforcement status — **Active**;
- Target branches → Add target → Include by pattern —
  `claude/website-copy-new-design-xaxsr0`;
- **Restrict deletions** и **Block force pushes** — включены;
- **Require a pull request before merging** — включено (Required
  approvals — 0: подтверждение второго человека не нужно);
- **Require status checks to pass** — включено, внутри:
  **Require branches to be up to date before merging** — включено;
  Add checks → `CI` (появится в списке после первой проверки на ветке).

Если в правилах уже требуются старые проверки `checks` или `image` — их
убрать: теперь они части «CI» и под прежними именами не появляются.

## Как устроен тестовый сервер

Одна машина Ubuntu 24.04, на ней три контейнера
([staging/compose.yml](staging/compose.yml)):

| Контейнер | Что делает |
|---|---|
| `caddy` | HTTPS (сертификат Let's Encrypt сам), пароль на весь сайт, передача запросов приложению. Заголовки `X-Forwarded-*` от посетителя отбрасывает и ставит свои — адрес посетителя и хост в ссылках из писем не подделать |
| `app` | тот же образ, что на Render ([Dockerfile](../Dockerfile)): Apache, сайт, админка, фоновые задачи. Собирается на самой машине |
| `db` | своя PostgreSQL 18 — та же версия, что на боевой, — с демо-данными, роль `savdex_django` — как на боевой базе. Наружу не открыта |

На машине:

```
/opt/savdex/src           код (git, переключается на выкладываемый коммит)
/opt/savdex/data          постоянный диск приложения (/var/data): загрузки, состояние расписания
/opt/savdex/pg            файлы базы (PostgreSQL 18: /opt/savdex/pg/18/docker)
/opt/savdex/env           пароли базы, APP_KEY, хеш пароля сайта — создаются на машине и её не покидают
/opt/savdex/current-tag   какая версия сейчас работает; releases.log — история выкладок
/opt/savdex/demo-data     отметка: на тестовом демо-данные, а не копия боевой базы
```

Данные тестового — свои, на диске самой машины: придуманные компании,
объявления и отзывы ([python/savdex/demo.py](../python/savdex/demo.py)),
а не копия боевой базы. Поэтому письма и SMS с тестового уходят
по-настоящему (ключи MAIL_* и TELNYX_* — с боевой, «От кого» —
«SAVDEX (тест)»), а у демо-учёток почты в зоне `.test`: на такие адреса
сайт писем не шлёт. Оплата и Telegram не подключены.

## Выкладка

[.github/workflows/staging.yml](../.github/workflows/staging.yml):

- каждый коммит основной ветки — сюда, когда на нём закончилась зелёная
  проверка «CI» (запуск по событию `workflow_run`): красный код на
  тестовый не попадает. Слияние появляется на тестовом минут через 15 —
  столько идёт «CI». Если проверки двух слияний закончились не по
  порядку, более старый коммит уже выложенный новый не заменяет;
- после выкладки — **проверка снаружи**, как посетитель, по HTTPS:
  `/up`, главная, `/catalog`, `/companies`, `/login`, `/register`,
  `/py/admin/login/` отвечают 200, на странице входа в админку — форма;
- прошла — коммит становится **кандидатом в релиз**: запись в GitHub →
  Environments → staging (Deployments API), со ссылкой на запуск. На
  боевые машины выкладывается кандидат («Боевые машины → Выкладка»);
- вручную (Actions → staging → Run workflow) — любая ветка, чтобы
  проверить её до слияния. Кандидатом такая выкладка не считается, а
  следующее слияние её заменит;
- один раз — подготовка чистой машины (галочка «bootstrap»,
  [server/bootstrap.sh](server/bootstrap.sh)): обновления, Docker,
  файрвол, SSH только по ключу, пользователь `deploy`.

[server/deploy.sh](server/deploy.sh) собирает образ, запускает, ждёт
ответа `/up`. Новая версия не поднялась — возвращает предыдущую и
красит workflow в красный.

Галочка «сбросить на демо-данные» (и «да» в подтверждении) стирает базу
и загруженные файлы тестового, создаёт схему и справочники заново и
заводит демо-данные — `manage.py demo`
([server/staging-reset.sh](server/staging-reset.sh)). На боевом
(`APP_ENV=production`) команда отказывается работать.

Галочка «ключи почты и SMS» один раз переносит с боевой машины сайта
настройки `MAIL_*` и `TELNYX_*` в настройки тестового
([server/env-merge.sh](server/env-merge.sh)) и перезапускает приложение
([server/staging-restart.sh](server/staging-restart.sh)). Значения в
журнал не выводятся. Работает только после сброса на демо-данные
(отметка `/opt/savdex/demo-data`): на копии боевой базы письма ушли бы
настоящим людям.

## Что нужно один раз

1. **Ключ для выкладки.** На своём компьютере (PowerShell или терминал):
   `ssh-keygen -t ed25519 -C savdex-deploy -f savdex-deploy` — без пароля
   на ключ. Получатся два файла: `savdex-deploy` (закрытый) и
   `savdex-deploy.pub` (открытый).
2. **Машина в UzCloud:** Ubuntu 24.04, 2 vCPU, 4 ГБ, диск 25 ГБ,
   публичный IP, открытые порты 22, 80, 443; при создании — открытый
   ключ `savdex-deploy.pub`.
3. **DNS у Ahost:** A-запись `staging` → IP машины.
4. **GitHub → Settings → Secrets and variables → Actions:**
   - секрет `DEPLOY_SSH_KEY` — содержимое файла `savdex-deploy` целиком;
   - секрет `STAGING_PASSWORD` — пароль на тестовый сайт (логин `savdex`);
   - переменная `STAGING_HOST` — IP машины;
   - переменная `STAGING_BOOTSTRAP_USER` — `root` или `ubuntu`, смотря
     под кем образ ОС пускает по ключу.
5. **Actions → staging → Run workflow** с галочкой «bootstrap». В
   журнале будет подсказка с ключом машины — сохранить его переменной
   `STAGING_HOST_KEY`.
6. **Для копии файлов — SSH на Render:**
   - Render → Account Settings → SSH Public Keys → Add SSH Public Key —
     содержимое `savdex-deploy.pub` (тот же ключ, что у выкладки);
   - Render → служба сайта → Connect → SSH — скопировать адрес вида
     `srv-…@ssh.oregon.render.com` в переменную `RENDER_SSH`. Ключ
     сервера SSH Render в Орегоне уже вписан в workflow (из документации
     Render); для другого региона — переменная `RENDER_SSH_HOST_KEY`.

Закрытый ключ и пароли — только в секреты GitHub, не в чат и не на
скриншотах. Репозиторий публичный: журналы Actions видят все, поэтому
скрипты пароли в журнал не пишут.

## Боевые машины

Три машины Ubuntu 24.04 в одной частной сети `savdex-prod` (тестовый
сервер — в другой сети и до боевой базы не дотягивается):

| Машина | Что на ней | Ресурсы |
|---|---|---|
| `savdex-web` | Caddy (HTTPS) и сайт. Адреса админки (`/py/admin`, `/py/login`, `/py/logout`) Caddy передаёт машине админки | 2 vCPU · 4 ГБ · 20 ГБ |
| `savdex-admin` | админка и фоновые задачи (расписание, перевод, письма и Telegram, ящик поддержки, сверка денег); здесь же собирается образ новой версии | 2 vCPU · 4 ГБ · 20 ГБ |
| `savdex-db` | PostgreSQL 18; общая папка загруженных файлов и кэша (NFS) для сайта и админки; резервные копии в S3 | 2 vCPU · 4 ГБ · 30 ГБ |

Наружу открыта только машина сайта: публичный IP сети переадресует на
неё порты 22, 80 и 443. Машины админки и базы видны только по частной
сети; GitHub Actions ходит к ним через машину сайта (ProxyJump). База
слушает только частный адрес своей машины, общая папка открыта только
частным адресам сайта и админки.

Как идёт запрос: посетитель → Caddy на машине сайта → сайт (Django) →
база и кэш. Файлы интерфейса и загрузки (`/storage/…`) Apache отдаёт
сам, из общей папки. Письма, Telegram и перевод сайт не делает в
запросе: он записывает задачу в базу, а фоновые задачи на машине
админки забирают её в течение минуты.

Код — тот же, что на Render; разница — в переменных роли
(`/opt/savdex/env/role.env`, его пишет
[server/prod-app.sh](server/prod-app.sh)):

- сайт — `SAVDEX_BACKGROUND=0` (без фоновых задач),
  `PYTHON_ADMIN_WORKERS=0` (без процесса админки);
- админка — фоновые задачи здесь, процесс сайта один и маленький;
- обе — `SAVDEX_MIGRATE=0`: схему базы меняет один разовый запуск
  `migrate` при выкладке, до перезапуска; `CACHE_STORE=file` и
  `SAVDEX_CACHE_DIR` в общей папке — правку настроек в админке сайт видит
  сразу.

На машинах:

```
/opt/savdex/src           код (переключается на выкладываемый коммит)
/opt/savdex/env           db.env — адрес базы с паролями (с машины базы);
                          app.env — настройки, перенесённые с Render;
                          role.env, compose.env, Caddyfile — пишет prod-app.sh
/opt/savdex/pg            файлы базы (только машина базы)
/srv/savdex/storage       общая папка: public, private, cache (только машина базы)
/opt/savdex/backup        журнал копий и три последние копии базы (машина базы)
/opt/savdex/current-tag   какая версия работает; releases.log — история
```

### Выкладка

[.github/workflows/prod.yml](../.github/workflows/prod.yml) — релизами.
Слияние в основную ветку сразу уходит только на тестовый сервер, а на
боевые машины — пачкой всё, что накопилось с прошлого релиза:

- **вручную:** Actions → prod → Run workflow — релиз сейчас;
- **по расписанию:** каждый вечер в 22:00 по Ташкенту, если включено
  (переменная `PROD_NIGHTLY_RELEASE` = `true`) и с прошлого релиза в
  основной ветке есть новое. Нового нет — машины не трогаются.

Что вошло в релиз — в сводке запуска (Summary): слитые PR с прошлого
удачного релиза. Порядок работы: слили PR — проверили на
`staging.savdex.uz` — релиз.

Каждый запуск:

1. Машина базы: [server/prod-db.sh](server/prod-db.sh) — PostgreSQL
   поднят, резервные копии в расписании; адрес базы — сайту и админке.
2. Машина админки: [server/prod-build.sh](server/prod-build.sh) —
   собирает образ и отправляет его на машину сайта по частной сети
   (ключ админки там может только `docker load`).
3. Машина админки: разовый `migrate` (схема, справочники), затем
   админка новой версии.
4. Машина сайта: сайт новой версии.

Не поднялось за несколько минут — машина возвращается на прежнюю
версию, запуск красный. Посетители при выкладке ошибок не видят: Apache
останавливается мягко (дорабатывает начатые запросы), новый — стартует,
когда Django уже готов, а Caddy, пока сайт перезапускается, держит
запрос и ждёт до минуты.

Изменения схемы базы должны быть совместимы с предыдущей версией кода:
`migrate` проходит до перезапуска сайта, и минуту-другую старый сайт
работает с новой схемой. Столбцы сначала добавляются, удаляются —
следующей выкладкой.

Галочки:

- «bootstrap» — подготовить чистые машины
  ([server/bootstrap.sh](server/bootstrap.sh) с ролями `web`, `admin`,
  `db`);
- «настройки с Render» — переменные окружения службы Render (APP_KEY,
  почта, оплата, Telegram, ключи Google…) по SSH на машины сайта и
  админки ([server/render-env.py](server/render-env.py)); в журнал идут
  только имена. Адрес базы и адрес сайта у новых машин свои;
- «копия с Render» — база и загруженные файлы с Render на новые
  машины; данные новых машин стираются, поэтому нужно ещё слово «да» в
  поле подтверждения. После переезда (`PROD_LIVE=true`) запрещена.

Пока адрес сайта (переменная `PROD_DOMAIN`) не `savdex.uz` — это
репетиция: сайт закрыт паролем тестового сервера (логин `savdex`).

### Резервные копии

С машины базы в хранилище S3 Uztelecom ([server/backup.sh](server/backup.sh),
cron пользователя `deploy`):

- база — каждую ночь в 03:40 по Ташкенту: `pg_dump`, проверка, шифрование
  тем же паролем, что у ночных копий Render (`BACKUP_PASSPHRASE`) —
  `uz/db/savdex-ГГГГ-ММ-ДД.dump.gpg`, 90 дней; три последние — ещё и на
  самой машине;
- файлы — каждый час, только новые и изменённые, зашифрованы
  (rclone crypt, тот же пароль) — `uz/files/`.

Восстановление — [docs/backups.md](../docs/backups.md).

### Что нужно один раз

1. **UzCloud:** сеть `savdex-prod` и три машины из таблицы выше (Ubuntu
   24.04, ключ `savdex-deploy.pub`, без своих публичных IP).
2. **UzCloud → сеть `savdex-prod` → публичный IP:**
   - переадресация портов на `savdex-web`: TCP 22, 80, 443 и UDP 443;
   - правила файрвола: TCP 22, 80, 443 и UDP 443.
3. **DNS у Ahost** на время репетиции: A-запись `new` → публичный IP
   сети `savdex-prod`. Запись `savdex.uz` — только в день переезда.
4. **GitHub → Settings → Secrets and variables → Actions → Variables:**
   - `PROD_HOST` — публичный IP сети `savdex-prod`;
   - `PROD_WEB_IP`, `PROD_ADMIN_IP`, `PROD_DB_IP` — частные адреса
     машин (10.…);
   - `PROD_DOMAIN` — `new.savdex.uz` на время репетиции.

   Секреты — те же, что уже есть: `DEPLOY_SSH_KEY`, `STAGING_PASSWORD`,
   `BACKUP_DATABASE_URL`, `BACKUP_PASSPHRASE`, `S3_ACCESS_KEY`,
   `S3_SECRET_KEY`; переменные `S3_ENDPOINT`, `RENDER_SSH`.
5. **Actions → prod → Run workflow** с галочками «bootstrap»,
   «настройки с Render», «копия с Render» и словом «да». В сводке
   запуска (Summary) — ключи машин: сохранить переменной
   `PROD_KNOWN_HOSTS`.
6. Проверить `https://new.savdex.uz`: сайт, вход, админка, картинки,
   письма (Telegram и письма уходят по-настоящему — настройки с Render).

На репетиции (адрес не `savdex.uz`) фоновые задачи выключены на обеих
машинах: база — копия боевой, а ключи почты, Telegram и ящика поддержки —
настоящие, с Render. Иначе люди получили бы письма второй раз, а письма
поддержки ушли бы из настоящего ящика в копию. Письма, которые сайт
шлёт сам в ответ на действия (код при регистрации, сброс пароля), на
репетиции уходят по-настоящему — тому, кто проверяет.

В день переезда фоновые задачи Render нужно выключить до того, как
включатся новые: иначе на двух площадках они пойдут дважды.

### День переезда

Простой для посетителей — минут 10–15, лучше ночью или рано утром.
Кто что делает: **В** — владелец (Render, Ahost, настройки GitHub),
**К** — Claude (запуск и проверка workflow).

Заранее, за несколько часов:

1. **В**, Ahost: у записей `savdex.uz` и `www` (если есть) TTL — `300`.
   Переезд — не раньше, чем пройдёт прежний TTL: до этого часть
   посетителей ещё будет попадать на Render.
2. **В**: проверить репетицию на `new.savdex.uz`.

Переезд:

1. **В**, Render → служба savdex → Environment: `SAVDEX_BACKGROUND=0`
   → Save. Render перевыкладывает сайт (несколько минут), и с этого
   момента он не шлёт писем и Telegram и не читает ящик поддержки —
   иначе на двух площадках это пошло бы дважды. Сайт на Render при
   этом работает.
2. **В**, GitHub → Variables: `PROD_DOMAIN` = `savdex.uz`.
3. **В**, Ahost: A-запись `savdex.uz` → публичный IP сети `savdex-prod`
   (и `www`, если есть, — туда же).
4. **К**: Actions → prod с галочками «настройки с Render», «копия с
   Render» и словом «да». Свежая копия базы и файлов, сайт на
   `savdex.uz` без пароля, фоновые задачи — на машине админки. Caddy
   получает сертификат, как только DNS указывает на новую машину;
   проверка снаружи ждёт до пяти минут.
5. **В**, как только **К** скажет, что копия снята: Render → служба
   savdex → Settings → **Suspend Web Service**. Всё, что посетители
   успели записать на Render после копии, не перенесётся — поэтому этот
   шаг сразу. База Render (savdex-db) остаётся как запасная.
6. **В**, GitHub → Variables: `PROD_LIVE` = `true`. С этого момента
   «копия с Render» запрещена, ночная копия базы Render выключена —
   копии снимает машина базы. Выкладка на новые машины — релизами
   (раздел «Выкладка» выше).
7. **В** и **К**: проверить вход, кабинет, админку, загрузку фото,
   письмо (например, сброс пароля), Telegram, оплату.

Если что-то пошло не так — вернуть: в Ahost запись `savdex.uz` обратно
на Render, Render → Resume, убрать `SAVDEX_BACKGROUND=0`. Записанное
на новых машинах за это время на Render не попадёт.
