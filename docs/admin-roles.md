# ТЗ: роли и права в админ-панели SavdEX

Документ описывает, что каждая из девяти ролей видит в панели управления,
что может делать и чего не может. Он же — приёмочный чек-лист: по разделу
[9](#9-приёмка) можно проверить готовую работу, не заглядывая в код.

---

## 1. Что заказано и что из этого уже есть

Ролей в панели сейчас **две**: `moderator` и `superadmin`. Права разложены
по девятнадцати файлам, тридцатью двумя вызовами `isSuperadmin()` и
`isModerator()`: либо полный доступ, либо ничего. Заказано девять ролей с разной глубиной доступа
и с возможностью выдать отдельному человеку дополнительное право.

Разделы панели на сегодня — двадцать:

| Группа | Разделы |
|---|---|
| Данные | Компании, Объявления, IT-задачи |
| Модерация | Документы на проверку, Отзывы, Жалобы на контакты |
| Монетизация | Счета и оплаты, Подписки, Тарифы, Промокоды, Пакеты контактов |
| Контент | Главная страница, Страницы и FAQ, Новости, Тендеры |
| Справочники | Категории, Типы компаний |
| Система | Пользователи, Рассылки, Настройки |

**Чего в коде нет совсем** и что придётся построить с нуля:

- CRM целиком: лиды, сделки, контакты, задачи, коммуникации;
- обращения в поддержку;
- возвраты и финансовые операции отдельным разделом;
- журнал действий администраторов;
- экран назначения ролей и прав.

Разделы «Поставщики» и «Покупатели» строить с нуля **не нужно**: у компании
уже есть поле `primary_role` со значениями `supplier`, `buyer`, `both`. Это
два отфильтрованных вида одного раздела «Компании», а не две новые таблицы.
Такое решение экономит этап работ и, главное, не разводит одну компанию по
двум карточкам, которые потом разойдутся в данных.

Подробнее о недостающем — раздел [6](#6-разделы-которых-ещё-нет).

## 2. Как устроен доступ

### 2.1. Три слоя

**Роль** — базовый набор прав. Одна роль на человека. Не «набор ролей»:
когда у сотрудника две роли, на вопрос «почему он это увидел» нет короткого
ответа, а именно этот вопрос задают после инцидента.

**Персональные добавки** — Super Admin может выдать конкретному человеку
право сверх его роли или, наоборот, отобрать. Это то самое «если Super Admin
отдельно не дал ему такое право» из задания. Хранится у пользователя, роль
при этом не меняется.

**Область видимости** — «свои записи» или «все записи». Продавец видит своих
лидов, руководитель — всех. Отдельным полем, а не удвоением списка прав.

Итоговый набор прав считается так:

```
права роли  +  персонально выданные  −  персонально отозванные
```

У Super Admin набор не считается вообще: ему разрешено всё, включая разделы,
которые появятся после написания этого документа. Иначе каждый новый раздел
пришлось бы отдельно выдавать владельцу системы, и однажды про это забудут.

### 2.2. Где проверяется

Прятать пункт меню — недостаточно. Панель раздаёт адреса вида
`/admin/payments`, и набрать такой адрес руками может кто угодно, у кого есть
вход. Поэтому проверка стоит **в трёх местах одновременно**, и каждое
закрывает свою дыру:

| Где | Что закрывает |
|---|---|
| Видимость пункта меню | Человек не видит того, что ему не нужно |
| Право на раздел (`canViewAny`) | Прямая ссылка на список записей |
| Право на запись (`canEdit`, `canDelete`) | Прямая ссылка на чужую карточку |

Правило для разработчика: **ни одна проверка права не пишется прямо в форме
или в таблице**. Все проверки — через единый слой прав, чтобы список
доступного считался в одном месте и там же проверялся тестами.

### 2.3. Что меняется в базе

У таблицы `users` уже есть колонки `is_admin` (пускать ли в панель) и
`admin_role` (что там видно). Разделение сохраняется: отозвать доступ целиком
одним полем проще, чем разбираться в роли.

Добавляется одна колонка — персональные добавки, в виде:

```json
{ "grant": ["payments.view"], "revoke": ["companies.delete"] }
```

Существующие значения `admin_role` менять не нужно: `moderator` и
`superadmin` остаются в новом списке под теми же именами. Ни одна строка при
переходе не переписывается.

### 2.4. Почему не готовый пакет ролей

Взвешивалось `spatie/laravel-permission`. Он даёт роли, которые заводят из
интерфейса, — но платит за это четырьмя таблицами, слоем кеша и тем, что
матрица прав перестаёт быть видна в коде и перестаёт проверяться тестами.

Здесь роли заданы заказчиком, их девять, и меняться они будут раз в год.
Матрица в коде + персональные добавки в базе закрывают задачу целиком: набор
прав виден в одном файле, проверяется тестами и едет вместе с релизом, а
разовые исключения выдаются из интерфейса без выкатки.

Пакет имеет смысл вернуть в обсуждение, если понадобится **заводить новые
роли из интерфейса**. Пока такой задачи нет.

## 3. Справочник прав

Право записывается как `раздел.действие`.

**Действия:**

| Действие | Что разрешает |
|---|---|
| `view` | Видеть раздел, открывать записи, пользоваться фильтрами |
| `create` | Создавать записи |
| `edit` | Изменять записи |
| `delete` | Удалять записи |
| `moderate` | Одобрить, отклонить, вернуть на исправление, скрыть |
| `export` | Выгружать список в файл |
| `import` | Загружать записи пачкой из файла |

**Разделы:**

| Группа | Разделы прав |
|---|---|
| Люди | `users`, `roles`, `audit` |
| Площадка | `companies`, `listings`, `tenders`, `ittasks` |
| Модерация | `documents`, `reviews`, `complaints` |
| CRM | `leads`, `deals`, `contacts`, `tasks`, `communications` |
| Поддержка | `support` |
| Финансы | `payments`, `subscriptions`, `plans`, `promocodes`, `creditpacks`, `refunds`, `finreports` |
| Контент | `content`, `catalogs`, `broadcasts`, `settings` |

`content` — это страницы, FAQ, новости, блоки главной и баннеры одним
правом: их правит один человек и незачем дробить.
`catalogs` — категории, отрасли, страны, города, типы компаний.

Отдельного права на «Поставщиков» и «Покупателей» нет: это виды раздела
`companies`, и ограничение задаётся областью видимости (см. 2.1).

## 5. Роли поимённо

### 5.1. Super Admin — владелец системы

**Стартовый экран:** дашборд целиком — площадка, воронка активации,
регистрации, деньги.

Видит все разделы без исключения, включая те, что появятся позже. Единственная
роль с доступом к экрану «Роли и права»: заводит сотрудников, назначает роли,
выдаёт и отзывает персональные права, отключает доступ.

**Граница:** её нет. Поэтому — два правила.

1. Роль выдаётся поимённо и по счёту. Норма — один-два человека.
2. Super Admin **не может снять роль сам с себя, если он последний**. Панель
   без владельца чинится только руками в базе.

### 5.2. Admin — администратор

**Стартовый экран:** дашборд без денежных показателей.

Ведёт рабочую часть площадки: пользователи, компании, товары, заявки,
поставщики, покупатели, контент и CRM целиком, без ограничения «свои».
Блокирует пользователей и компании, правит их данные.

**Не видит:** финансовый раздел (счета, подписки, тарифы, возвраты, отчёты)
и экран «Роли и права».

**Граница:** Admin правит карточку пользователя, но **не может выдать себе
или другому права администратора** — переключатель «Администратор» и выбор
роли на форме пользователя видны только Super Admin. Иначе граница между
Admin и Super Admin существует ровно до первой попытки её обойти.

Доступ к финансам выдаётся персонально, правом `payments.view`.

### 5.3. Sales — отдел продаж

**Стартовый экран:** свои лиды и задачи на сегодня.

Видит: Лиды, Сделки, Контакты, Задачи, Коммуникации, Компании.

Создаёт и правит **свои** лиды и сделки, меняет их статусы, ведёт клиентов.
Заводит и правит промокоды: назвать клиенту код и выдать его — часть сделки,
а не отдельная заявка в другой отдел. Удалять промокоды продавец не может.

Компании — только смотрит: карточку компании ведёт её владелец или менеджер
направления, продавец работает с лидом.

**Не видит:** настройки сайта, пользователей, платежи, финансовую аналитику.

**Что значит «свои»:** записи, где продавец указан ответственным. Лид без
ответственного виден всем продавцам — иначе новые заявки зависнут. Передача
лида другому продавцу — действие в карточке, доступное Admin и Super Admin.

### 5.4. Supplier Manager — работа с поставщиками

**Стартовый экран:** новые поставщики и их документы на проверке.

Видит компании с ролью «поставщик» и связанные с ними лиды, контакты и
заявки. Добавляет поставщиков, правит карточки, ведёт работу, передаёт на
модерацию.

**Не видит:** финансовый раздел, настройки, внутренние данные покупателей
глубже общего списка компаний.

**Граница:** передаёт на модерацию, но **не модерирует сам**. Проверять то,
что сам завёл, — не проверка. Одобряет Moderator.

При этом менеджер **видит всё, что завёз**, и видит состояние проверки: что
ждёт очереди, что одобрено, что вернули с комментарием. Иначе передача на
модерацию превращается в отправку в пустоту.

### 5.5. Buyer Manager — работа с покупателями

**Стартовый экран:** новые покупатели и необработанные запросы.

Видит компании с ролью «покупатель», их потребности и запросы. Создаёт и
правит карточки покупателей, обрабатывает запросы, связывает их с подходящими
поставщиками.

**Не видит:** финансовый раздел, административные настройки.

**Граница:** та же, что у Supplier Manager, — модерация чужая.

### 5.6. Moderator — модерация

**Стартовый экран:** очередь на проверку с разбивкой по типам и счётчиком
ожидания. Самое старое — сверху.

Видит только то, что требует проверки: компании, товары, услуги, объявления,
потребности, документы и изображения.

**Четыре решения по каждой записи:**

| Решение | Что происходит |
|---|---|
| Одобрить | Публикуется, автор получает уведомление |
| Вернуть на исправление | Возвращается автору с комментарием, автор правит и шлёт снова |
| Отклонить | Не публикуется, причина обязательна, повторная подача — новой записью |
| Скрыть | Уже опубликованное снимается с витрины |

«Вернуть на исправление» и «Отклонить» — **разные исходы**, и в базе им
нужны разные статусы. Сейчас статус один, `rejected`; добавляется
`needs_changes`. Разница видна автору: в первом случае он правит и
продолжает, во втором начинает заново.

**Комментарий обязателен** для «вернуть» и «отклонить». Отказ без причины
возвращается в поддержку вопросом «а почему».

**Не видит:** платежи, зарплаты, настройки пользователей, внутреннюю CRM.

### 5.7. Finance — финансы

**Стартовый экран:** платежи за сегодня и то, что ждёт проверки.

Видит финансовые разделы: платежи, подписки, счета, возвраты, финансовые
операции и отчёты. Проверяет оплаты, проводит разрешённые операции.

**Не видит:** содержимое CRM, административные настройки.

**Границы, которые в финансах важнее прочего:**

1. Тарифы — **только чтение**. Цена тарифа меняет счета всем подписчикам
   сразу; это решение владельца, а не операционное действие.
2. Возврат и ручное изменение баланса **пишутся в журнал** с указанием
   автора, суммы и причины. Причина обязательна.
3. Проведённый платёж **не удаляется**. Ошибка исправляется обратной
   операцией — так остаётся история.

### 5.8. Support — поддержка

**Стартовый экран:** открытые обращения, свои — сверху.

Видит пользователей, компании и обращения. Открывает карточку пользователя,
историю обращений, техническую информацию: тариф, остаток контактов, даты
входов, статус компании, отправленные уведомления.

**Не видит:** финансовое управление (суммы платежей, возвраты, отчёты),
настройки ролей.

**Граница между «видит» и «правит»:** поддержка смотрит и отвечает, но не
правит данные пользователя — **никаких исключений**. Любая правка, включая
письмо для смены пароля, идёт заявкой к Admin. Решение заказчика: если
объём таких заявок окажется неподъёмным, границу пересмотрим по факту, а
не заранее.

Support видит, что подписка активна и до какого числа, но не видит, сколько
за неё заплачено.

### 5.9. Content Manager — контент

**Стартовый экран:** страницы и новости, черновики сверху.

Видит управление публичным содержимым: категории, страны, отрасли, страницы,
новости, баннеры, FAQ, информационные материалы.

**Не видит:** финансы, пользователей, CRM.

**Граница:** категории и страны — это справочники, на которые ссылаются
тысячи объявлений. Переименовать можно, **удалить непустую — нельзя**:
удаление доступно, только если на запись никто не ссылается. Иначе одно
неосторожное действие уносит с витрины целый раздел каталога.

## 6. Разделы, которых ещё нет

Это не доработка существующего, а отдельная работа. Перечислено, что именно
предстоит построить.

### 6.1. CRM

Пять сущностей:

**Лид** — обращение, из которого может вырасти клиент. Источник, контактное
лицо, компания (если уже есть в базе), ответственный, статус, комментарии.
Статусы: новый → в работе → квалифицирован → сделка / отказ.

**Сделка** — работа с конкретным клиентом по конкретной сумме. Компания,
ответственный, сумма, валюта, этап, ожидаемая дата закрытия, причина отказа.

**Контакт** — человек. Имя, должность, телефон, почта, компания. Отдельно от
пользователя площадки: контакт может не быть зарегистрирован, а у компании
контактов несколько.

**Задача** — что сделать и к какому сроку. Исполнитель, срок, связь с лидом
или сделкой, отметка о выполнении.

**Коммуникация** — запись состоявшегося разговора: звонок, письмо,
встреча, сообщение. Дата, участники, содержание, связь с лидом или сделкой.

Связь с существующим: лид и сделка ссылаются на `companies`, ответственный —
на `users`. Ничего из этого не дублирует то, что уже есть.

**Отдельно решить:** нужна ли интеграция с почтой и телефонией. Пока
коммуникации заводятся руками.

### 6.2. Обращения в поддержку

Тема, автор, статус (открыто / в работе / ждёт ответа / закрыто),
ответственный, переписка, вложения, связь с пользователем и компанией. Канал
поступления: форма на сайте, почта, звонок.

### 6.3. Финансовые разделы

Платежи (`payments`), транзакции (`payment_transactions`), кошельки
(`wallets`, `wallet_transactions`) и подписки в базе **уже есть**. Отсутствуют:

- **Возвраты** — отдельная запись со ссылкой на платёж, суммой, причиной,
  автором и статусом;
- **Финансовые отчёты** — выручка по периодам, по тарифам, по источникам;
  продления и отток;
- **Экран сверки**: что площадка начислила против того, что пришло от
  платёжного шлюза.

### 6.4. Журнал действий администраторов

Без него девять ролей не имеют смысла: разграничение, которое нельзя
проверить постфактум, — это договорённость, а не защита.

Пишется: кто, когда, что сделал, с какой записью, что было и что стало, с
какого адреса. Не пишутся операции чтения — иначе журнал утонет в шуме.

Обязательно попадают в журнал: выдача и отзыв прав, блокировка пользователя и
компании, любое решение модерации, любая финансовая операция, изменение
настроек площадки, любая выгрузка данных.

**Журнал не редактируется и не удаляется из интерфейса — никем, включая
Super Admin.** Срок хранения — год.

### 6.5. Экран «Роли и права»

Список сотрудников с ролями. По каждому: назначить роль, выдать или отозвать
отдельное право, отключить доступ. Рядом с каждым правом — что оно открывает,
словами. Видно, какие права человек получил персонально, а какие — от роли.

### 6.6. Справочники, которых нет в панели

Страны и города в базе есть (`countries`, `cities`), но в панели их нет —
нужны разделы. Баннеры — решить, отдельная это сущность или хватит блоков
главной страницы.

## 7. Общие правила

**Вход.** Доступ в панель даёт флаг «Администратор». Роль определяет, что
внутри. Заблокированный сотрудник не входит независимо от роли.

**Прямые ссылки.** Любой адрес панели, на который у роли нет права, отдаёт
отказ. Не пустую страницу, не список без записей — отказ. Проверяется тестами
по каждой роли.

**Стартовый экран.** У каждой роли свой, из раздела 5. Продавец, попадающий
на дашборд с выручкой площадки, — это утечка, оформленная как удобство.

**Выгрузки.** Право `export` отдельно от `view`: посмотреть список на экране
и унести его файлом — разные по последствиям действия. Каждая выгрузка
пишется в журнал.

**Удаление.** Компании, объявления и пользователи удаляются мягко и
восстановимы. Право на окончательное удаление — только у Super Admin.

**Персональные данные.** Телефоны и почты в карточках компаний Sales,
Supplier Manager и Buyer Manager видят полностью — это их работа. Support
видит. Content Manager не видит карточек компаний вовсе.

**Смена роли** действует со следующего запроса, без перезахода. Отзыв
доступа — немедленно, с завершением активных сессий сотрудника.

## 8. Решения по спорным местам

В задании этих пунктов не было; они выведены из соседних требований и
согласованы с заказчиком 14 сентября 2026 года. Здесь записан итог, а не
предложение.

1. **Одна роль на человека**, а не набор ролей. Причина — раздел 2.1.
2. **Sales заводит промокоды сам** — смотрит, создаёт, правит. Удалять не
   может. *Решение заказчика; изначально предлагалось только чтение.*
3. **Sales видит компании на чтение**, а правит только лиды и сделки.
4. **Supplier и Buyer Manager не модерируют** то, что сами завели, но
   **видят всё, что завезли, и состояние проверки**. Buyer Manager получил
   доступ к документам на чтение по той же причине. *Уточнение заказчика.*
5. **Admin не видит финансы вообще** — ни сумм, ни отчётов. В задании сказано
   «не видит финансовый раздел»; трактовано буквально.
6. **Finance видит тарифы только на чтение** — раздел 5.7.
7. **Support не правит данные пользователя ни в каком виде**, включая письмо
   для смены пароля: всё идёт заявкой к Admin. *Решение заказчика; изначально
   предлагалось сделать исключение для смены пароля. Если поток заявок
   окажется неподъёмным, границу пересмотрим по факту.*
8. **Moderator видит справочники на чтение** — категории, отрасли, страны,
   типы компаний. Иначе непонятно, в ту ли категорию подано объявление.
   Справочники — одно право, дробить его на пять ради одной роли незачем.
9. **«Вернуть на исправление» — новый статус** `needs_changes`, отдельный от
   «отклонить». *Подтверждено заказчиком; сделано. Заодно выяснилось, что
   отклонение ничего не значило: автор возвращал снятое объявление
   на витрину одним нажатием «опубликовать заново».*
10. **Поставщики и покупатели — виды раздела «Компании»**, а не отдельные
    разделы. Раздел 1.
11. **Выгрузка и загрузка выдаются поимённо**, а не вместе с правом на
    правку: Admin выгружает и загружает компании и тендеры, выгружает
    объявления и пользователей; Finance выгружает платежи, подписки и
    финансовые отчёты; остальные роли не выгружают ничего. *Решение принято
    при реализации: выгрузка уносит персональные данные целым файлом,
    загрузка создаёт записи пачкой мимо форм и их проверок.*

## 9. Приёмка

Проверяется под каждой ролью отдельно, на живых учётных записях.

**По каждой из девяти ролей:**

| № | Проверка | Ожидание |
|---|---|---|
| 1 | Войти и посмотреть меню | Только разделы своей строки матрицы |
| 2 | Открыть стартовый экран | Экран из раздела 5, без чужих показателей |
| 3 | Набрать руками адрес запрещённого раздела | Отказ, не пустая страница |
| 4 | Набрать адрес чужой карточки | Отказ |
| 5 | Открыть разрешённый раздел | Список открывается, фильтры работают |
| 6 | Попробовать запрещённое действие в разрешённом разделе | Кнопки нет, прямой вызов отклонён |

**Отдельные проверки:**

| № | Проверка | Ожидание |
|---|---|---|
| 7 | Admin открывает `/admin/invoices` | Отказ |
| 8 | Admin открывает форму пользователя | Переключателя «Администратор» нет |
| 9 | Moderator открывает счета или подписки | Отказ |
| 10 | Sales открывает чужой лид | Отказ |
| 11 | Sales открывает лид без ответственного | Открывается |
| 12 | Support открывает подписку | Видит срок, не видит сумму |
| 13 | Content Manager удаляет категорию с объявлениями | Отказ с объяснением |
| 14 | Finance меняет цену тарифа | Поля недоступны |
| 15 | Super Admin выдаёт Admin право `payments.view` | Раздел появляется без перезахода |
| 16 | Он же отзывает право | Раздел исчезает немедленно |
| 17 | Super Admin снимает роль с себя, будучи последним | Отказ |
| 18 | Сотрудника блокируют во время работы | Следующее действие — на экран входа |
| 19 | Moderator возвращает объявление на исправление без комментария | Форма не отправляется |
| 20 | Любое действие из списка 6.4 | Появилось в журнале с автором и временем |
| 21 | Кто угодно пробует изменить запись журнала | Такой возможности нет |

**Что проверяется тестами, а не руками:** пункты 3 и 4 по каждому разделу
каждой роли — это без малого триста сочетаний. Ручная проверка их пропустит.

## 11. Где это в коде

Этап 1 сделан. Что появилось:

| Файл | Что в нём |
|---|---|
| `app/Support/AdminAccess.php` | Матрица, роли, справочник прав, область видимости. Единственное место, где записано, кто что может |
| `app/Support/AdminScope.php` | Сужение списка до «своих записей» — запросом, а не скрытием строк |
| `app/Support/AdminLog.php` | Запись в журнал: одна точка входа для наблюдателя и для служб |
| `app/Filament/Concerns/AuthorizesBySection.php` | Трейт ресурса: объявляет раздел прав, остальное берёт из матрицы |
| `app/Observers/AuditObserver.php` | Ловит правки администратора в панели |
| `app/Providers/AppServiceProvider.php` | Гейты и карта «модель → раздел» для журнала |
| `app/Models/User.php` | `hasAdminAbility()`, `adminAbilities()`, `adminScopeIsOwn()` |
| `app/Models/Crm/` | Лид, сделка, контакт, задача, коммуникация |
| `app/Models/Support/` | Обращение и сообщение в нём |
| `app/Models/Refund.php`, `app/Services/Payments/RefundService.php` | Возвраты |
| `app/Filament/Pages/Roles.php` | Экран «Роли и права» |
| `app/Filament/Pages/FinanceOperations.php` | Лента движений по кошелькам |
| `tests/Feature/{Admin,Crm,Support,Finance}/` | Роли, журнал, CRM, обращения, возвраты |

**Как добавить раздел прав.** Дописать строку в `AdminAccess::SECTIONS`, выдать
его нужным ролям в `MATRIX`, поставить ресурсу `$accessSection`. Больше нигде
ничего править не нужно — и не нужно ничего не забыть.

**Что закрылось попутно.** Отзывы, тендеры, IT-задачи и документы на проверку
не объявляли прав вовсе и потому открывались любому, кто вошёл в панель.
Массовое удаление в рассылках, IT-задачах, тендерах, новостях и категориях —
тоже. Загрузка тендеров из файла — тоже.

**Что осталось.** Все восемь этапов закрыты. За их пределами остаются
автоматизация (лиды, обращения и звонки заводятся руками) и инфраструктура —
см. [отдельный документ](backlog.md).

**Два места, где ждут решения.** Интеграция CRM с почтой и телефонией —
пока коммуникации заводятся руками. Статус «вернуть на исправление»
(`needs_changes`) согласован, но делается вместе с очередью модерации.

**Чему научил PostgreSQL.** Два дефекта журнала на SQLite не проявлялись
вовсе: внешний ключ на автора не давал записать удаление сотрудника, а
проглоченная ошибка внутри чужой транзакции отменяла саму операцию,
которую журнал записывал. Проверять оба движка стоит до выкатки, а не
после.
