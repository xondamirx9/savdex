# Перенос площадки с PHP на Python

Техническое задание на постепенный перенос SavdEX с Laravel на Django.

Заведён потому, что решение принято по кадровой причине — наши
программисты не знают PHP, — а такой перенос стоит года работы и может
тихо развалиться в середине, если не записать заранее, что и в каком
порядке двигается. Здесь записан порядок и записаны ловушки.

Отличается от [списка работ](backlog.md): там текущие задачи по
работающему сайту, здесь — отдельная многомесячная работа рядом с ними.

Отдельно стоит сказать про 25 тысяч строк тестов. Как код они

одно правило площадки. Это и есть спецификация переноса. Порядок такой:
взяли тест на PHPUnit → повторили его сценарий на pytest → написали код,
который его проходит. Ни одна часть не считается перенесённой, пока её
тесты не повторены.

## 2. Почему Python, а не Java

Решение не про языки вообще, а про этот код.

**Админка — треть всего бэкенда.** 14 604 строки на Filament. В Python
прямой аналог есть — админка Django, она закрывает большую часть того же
самого: списки с фильтрами, формы, права по разделам, массовые действия.
В Java аналога нет: Spring Boot генератора разделов не даёт, и эти 30
разделов пришлось бы писать руками целиком. По опыту это в три-пять раз
больше кода, чем сейчас. Один этот пункт перевешивает всё остальное.

**Фронтенд остаётся.** У нас Inertia и React — 17 149 строк TypeScript.
У Inertia есть поддерживаемый адаптер для Django. Страницы React меняются
минимально: тот же формат данных, тот же способ навигации. Под Java
серьёзного адаптера Inertia нет — весь фронтенд пришлось бы переводить
на отдельный API и переписывать каждую страницу.

**Модели ложатся один в один.** Eloquent и Django ORM устроены одинаково:
модель знает свою таблицу, у неё есть миграции, есть события при
сохранении (в Django — сигналы). Eloquent → JPA/Hibernate — смена
подхода целиком: отсоединённые сущности, ленивая загрузка с исключениями,
отдельный слой репозиториев. На той же логике выходит заметно больше кода
и заметно больше новых ошибок.

**Память.** 2 ГБ на Render, и 18 сентября сайт уже падал по памяти
([разбор](backlog.md)). JVM в этих рамках живёт хуже Python.

**Когда выбрали бы Java.** Если команда знает только Java и Python для
неё такой же чужой, как PHP. Тогда знание команды важнее удобства
переноса, и план придётся переписать: сначала разделение на API,
потом фронтенд, админка — руками и последней. Если это наш случай —
скажите до начала этапа 0, а не после.

Версии на старте: Python 3.12, Django 5.x, тот же PostgreSQL 16.

## 3. Как переносим: удушающий фикус

Перед сайтом ставится обратный прокси (nginx). Он смотрит на путь запроса
и отправляет его либо в старый Laravel, либо в новый Django. **База одна
и та же.** Оба приложения работают одновременно, сколько понадобится.

> **Как сделано на деле (этап 2).** Отдельного nginx нет: роль прокси
> играет Apache, который уже стоит в службе Render. Django (gunicorn)
> запущен в том же контейнере на `127.0.0.1:8001`, и Apache передаёт
> ему только пути из `docker/apache-python.conf`. Одна служба — нет
> второй строки в счёте и второй базы настроек; откат — убрать строку
> из этого файла и передеплоить. Подробно — «Этап 2. Порядок работ».

```
                    ┌─────────────┐
   посетитель  ───► │    nginx    │
                    └──┬───────┬──┘
           /companies  │       │  /catalog, /admin, ...
            (перенесли)│       │  (ещё не перенесли)
                       ▼       ▼
                 ┌────────┐ ┌─────────┐
                 │ Django │ │ Laravel │
                 └────┬───┘ └────┬────┘
                      └─────┬────┘
                       ┌────▼─────┐
                       │PostgreSQL│
                       └──────────┘
```

Что это даёт:

- **Откат — одна строка в конфиге прокси.** Перенесённый кусок повёл себя
  не так — вернули путь на Laravel, разбираемся спокойно.
- **Сайт не останавливается ни на день.** Требование заказчика выполнено
  буквально: переносим кусками, целиком не кладём.
- **Схему базы заново описывать не надо.** `python manage.py inspectdb`
  сгенерирует модели Django по существующим 74 таблицам.

## 4. Три правила, которые нельзя нарушать

Эти три ломают базу молча, и обнаружится это через недели.

### 4.1. У каждой таблицы один хозяин на запись

В любой момент времени **писать в таблицу может только одна сторона** —
либо Laravel, либо Django. Вторая читает. Переход хозяина — отдельный,
запланированный шаг, а не побочный эффект.

Причина в разделе 5: половина правил площадки живёт в событиях моделей
Laravel, и код на Django, пишущий в ту же таблицу, обойдёт их молча.

Как держится технически: в Django у модели ставится
`class Meta: managed = False` — Django не будет трогать её схему, — а на
запись вешается запрет, пока хозяин не перешёл. Карта хозяев — раздел 6.

Единственное исключение — `admin_actions`, журнал действий: в него
с этапа 2 пишут обе стороны. Почему это безопасно — раздел 5.1.

### 4.2. Миграции запускает только одна сторона

Хозяин схемы до самого конца — **Laravel**. Все изменения структуры базы
идут через `database/migrations`, даже если таблицу уже читает и пишет
Django. Django-миграции не применяются вовсе (`managed = False` у всех
моделей, взятых из существующей базы).

Иначе получим две истории миграций, которые про одну базу думают разное,
и первый же откат снесёт чужие изменения.

Django перейдёт в хозяева схемы на последнем этапе, когда Laravel уйдёт
совсем.

### 4.3. Ни одна часть не переносится без повторённых тестов

Тест на pytest, повторяющий сценарий существующего теста PHPUnit,
пишется **до** кода и должен падать без него. Ровно так проверялись
исправления в сентябре: без этого правила «перенесено» означает
«скомпилировалось».

## 5. Невидимый договор: правила в событиях моделей

Самая опасная часть переноса. Тринадцать моделей выполняют правила
площадки **при сохранении**, а не в контроллере. Значит, код на Django,
который пишет в ту же таблицу напрямую, обойдёт их и не сообщит об этом.

Ровно этот класс ошибок находился при проверке сайта 18 сентября: правило
стояло в одном из четырёх путей, три остальных его не знали.

Перед тем как Django получает право писать в таблицу, каждое правило из
этой таблицы должно быть перенесено и закрыто тестом.

| Модель | Когда | Что делает | Чем грозит пропуск |
|---|---|---|---|
| `AdminAction` | изменение, удаление | **Бросает исключение.** Журнал действий администраторов неизменяем | Журнал перестаёт быть доказательством. Это свойство безопасности, не удобство |
| `Listing` | сохранение | **Отклонённое объявление не возвращается на витрину** (кроме модератора). Путей в статус «активно» четыре | Снятое модератором объявление возвращается само |
| `Listing` | сохранение | Пересборка `search_text` — обе графики плюс переводы | Объявление пропадает из поиска |
| `Listing` | после сохранения | Постановка задачи на перевод при публикации | Объявление остаётся без переводов |
| `Review` | после сохранения | Пересчёт рейтинга компании. При переезде отзыва — **обеих** компаний | Рейтинг расходится с отзывами. По нему покупатель выбирает поставщика |
| `Review` | после удаления | Тот же пересчёт | То же |
| `Company` | создание | Адрес из названия с транслитерацией кириллицы и узбекской латиницы | Пустой или повторяющийся адрес визитки |
| `Company` | сохранение | `search_text` в обеих графиках | Компания не находится поиском |
| `Setting` | сохранение, удаление | Сброс кэша настроек — и в хранилище, и в памяти запроса | Настройка «не сохраняется» на глазах у администратора |
| `Promotion` | сохранение | `active_key` — эмуляция частичного уникального индекса | Два активных продвижения на одном объявлении |
| `Banner` | изменение, удаление | Удаление файлов картинок, включая языковые | Диск засоряется навсегда |
| `BannerImage` | изменение, удаление | То же для языковой картинки | То же |
| `ItTask` | сохранение, создание | `search_text`; адрес строится из id, то есть после вставки | Задача не находится, адрес пустой |
| `Tender` | сохранение, создание | То же | То же |
| `Resume` | сохранение | **Сброс переводов при правке текста.** Старый перевод новой должности не устарел, а врёт | Резюме показывает неправду на других языках |
| `Resume` | после сохранения | Перевод опубликованного | Резюме без переводов |
| `NewsPost` | после сохранения | Перевод новости | Новость без переводов |
| `Country` | сохранение | Код страны к нижнему регистру | Фильтр по стране не находит ничего |

### 5.1. Журнал действий — сквозное правило

Кроме событий в самих моделях есть **`App\Observers\AuditObserver`**.
Он подключается в `AppServiceProvider` сразу к **26 моделям** — от
`User` и `Company` до `Payment` и `Setting` — и на каждое создание,
изменение и удаление пишет строку в `admin_actions`: кто, что, какое
поле, было и стало.

Это не относится ни к одному этапу — это относится **ко всем**. Как
только Django получает право писать в таблицу любой из этих 26 моделей,
он обязан писать и в журнал. Иначе правки, сделанные через новую
половину сайта, в журнале не появятся, и журнал перестанет отвечать
на вопрос, ради которого заведён: кто это сделал.

Отсюда **исключение из правила 4.1**: в `admin_actions` с этапа 2 и до
конца пишут обе стороны. Это безопасно ровно потому, что таблица
добавляемая: строки только дописываются, а `AdminAction` запрещает
изменение и удаление (раздел 5). Двум писателям нечего не поделить.

Перенос наблюдателя — часть этапа 2, вместе с первой таблицей,
переходящей к Django, а не часть этапа 6, где переезжает сам раздел
журнала в админке.

### 5.2. Поиск

Отдельно: **`App\Support\SearchText`**. Его используют пять моделей, и он
задаёт, как текст попадает в индекс и как разбирается запрос —
транслитерация кириллицы и узбекской латиницы в обе стороны. Переносить
его надо **побайтово точно**: если Django индексирует иначе, чем Laravel,
поиск начнёт вести себя по-разному на соседних страницах одного сайта,
и понять это по симптомам почти невозможно. Это первый кандидат на
перенос и на тест «те же сто строк дают тот же результат в обеих
реализациях».

## 6. Карта таблиц: кто хозяин на каждом этапе

74 таблицы. «Хозяин» — сторона, которой разрешена запись. До своего

`sessions` (1) — **особый случай**, см. этап 3.

Обновляется по мере переноса, чтобы не восстанавливать положение
дел по истории правок.

|---|---|

| Этап 0, стенд с копией боевой базы | **ждёт Render** |
| Этап 0, прокси перед сайтом | сделано: Apache в той же службе передаёт Django пути из `docker/apache-python.conf`; пока только служебный `/py/up` |
| Этап 1, неделя 1: `savdex:check-postgres` | сделано |
| Этап 1, неделя 2: `savdex:uzum-ping` | сделано |
| Этап 1, недели 3–4: `savdex:export-xlsx` | сделано; на боевом сервере **скачиваются книги Python-версии**, PHP-версия в тени для сверки (кнопка в админке) |
| Python в боевом образе Docker | сделано; сборка проверяется в CI (`docker.yml`) |
| Этап 1, неделя 5: `savdex:admin` | сделано; Python-команда `admin` сверена с PHP на одной базе и проверена на боевом сервере: выданный ею пароль принят при входе в админку |
| **Этап 1 целиком** | **закрыт**: все четыре команды работают на Python на боевом сервере |

Что выяснилось по дороге:

- **Предохранители первой правки не работали.** Получатель сигнала
  `connection_created` регистрируется при импорте модуля, а импортировать
  его было некому: ссылки в `DATABASE_ROUTERS` мало, маршрутизатор Django
  создаёт лениво — уже после соединения. Запись в чужую таблицу доходила
  до базы. Все проверки при этом проходили, потому что тестовый файл
  импортирует модуль сам. Починено через `AppConfig.ready()`, закрыто
  проверкой в отдельном процессе.
- **Сверка двух выводов работает.** Порт `check-postgres` насчитал
  на одну таблицу больше, чем PHP-версия: проба прав создавала временную
  таблицу, и та доживала до подсчёта схемы в том же соединении. Само
  число «76 таблиц» ничем не выдавало подделку. Отсюда правило на будущее:
  **каждую перенесённую команду прогонять обеими реализациями
  и сравнивать вывод построчно**, а не только смотреть, что она
  отработала.
- **Вчерашняя миграция проверена на PostgreSQL.** Частичный уникальный
  индекс по отзывам применился на настоящем сервере, а не только
  на SQLite, — заодно, при подготовке стенда.
- **Перенос находит ошибки в оригинале.** При переносе `uzum-ping`
  выяснилось, что маскировка адреса прокси обрывалась на первом «@»
  и выпускала наружу хвост пароля: `http://user:***@ss:word@host`.
  Вывод команды вставляют в задачу и пересылают в переписке, так что
  это настоящая утечка. Исправлено **в обеих** половинах: чинить копию
  и оставлять работающий код как есть — бессмысленно.
- **Собственная сверка слепа к ошибке своего же чтения.** Выгрузка
  проверяет себя: перечитывает файл и сверяет с повторным запросом
  к базе. Но запрос идёт тем же путём, что и при записи, и если этот
  путь врёт — обе стороны врут одинаково. Так было с полями JSON:
  драйвер Python разбирал их в словари, а при сборке обратно
  менялись пробелы и экранирование кириллицы. Python-версия честно
  отвечала «все листы сошлись» — при двух расхождениях с PHP. Поймать
  такое может только **сравнение двух реализаций**, поэтому оно
  теперь постоянно в CI (`python/tests/test_export_parity.py`).
- **Крайние случаи надо проверять на то, что они крайние.** Первое
  наполнение базы было слабым: сравнение проходило и с ошибкой
  в чтении JSON. Отсюда тест, который проверяет, что нужные крайние
  случаи действительно попали в выгрузку, — иначе сравнение однажды
  снова тихо ослепнет.
- **Первый запуск Python из PHP уронил Django на старте.** Laravel
  задаёт `LOG_LEVEL=debug` строчными и знает восемь уровней PSR-3, а
  журнал Python понимает пять и прописными. PHP передаёт Python своё
  окружение целиком, и одноимённая переменная с другими соглашениями
  ломала настройки. Общие переменные окружения — место, где две
  половины будут сталкиваться и дальше; проверять надо запуском
  с настоящим окружением Laravel, а не с аккуратно собранным для теста.
- **Выравнивание в выводе PHP до экрана не доходит.** `SymfonyStyle`
  схлопывает пробелы, и столбцы, расставленные в исходнике `uzum-ping`,
  не видны. При сверке двух выводов отступы поэтому нормализуются
  (`sed 's/  */ /g'`), а Python-версия печатает так, как задумывал
  автор PHP-версии.

### Этап 1. Команды и диагностика (3–4 недели)

### Этап 2. Справочники и содержимое (6–8 недель)

Первый переход хозяина таблиц. Первый настоящий раздел админки Django.

Перед переходом каждой таблицы — перенести её правила из раздела 5.

#### Порядок работ

1. **Распределитель адресов** ✅. Django запущен в той же службе Render
   (gunicorn на `127.0.0.1:8001`, `docker/render-entrypoint.sh`), Apache
   передаёт ему пути из `docker/apache-python.conf`. Падение Django
   видно только на его адресах (503), остальной сайт не замечает;
   gunicorn поднимается сам через пять секунд. Память: заложено 200 МБ
   (замер — около 110 МБ на два процесса), это минус три-четыре процесса
   Apache на тарифе 2 ГБ. Проверка в CI запускает контейнер целиком
   и ходит в Laravel и в Django через настоящий Apache.
2. **Вход в админку Django** ✅. Своих таблиц пользователей и сессий у
   Django нет, чтение сессии Laravel — задача этапа 3. Поэтому пропуск
   от Laravel:
   - пункт «Админка на Python» в меню Filament ведёт на `/admin/python`
     (за входом в админку и сменой выданного пароля);
   - Laravel (`App\Support\PythonBridge`) отдаёт страницу, которая
     POST-ом приносит в Django пропуск: номер, адрес, срок в 60 секунд,
     подпись HMAC-SHA256 ключом, выведенным из `APP_KEY` (не им самим);
     POST — чтобы пропуск не оседал в журналах и истории браузера;
   - Django (`python/savdex/bridge.py`) проверяет подпись и срок, заново
     читает пользователя из базы (администратор, активен, не удалён,
     пароль сменён) и ставит свою подписанную куку на `/py/`, на два
     часа; `SECRET_KEY` Django тоже выведен из `APP_KEY`, без него
     вход выключен — подпись известным всем ключом подделал бы кто угодно;
   - на каждом запросе пользователь перечитывается: блокировка или
     снятая роль действуют сразу;
   - права — копия AdminAccess (`python/savdex/access.py`), совпадение
     с PHP сверяется по всем 210 правам для 14 разных сотрудников
     (`tests/test_access_parity.py`).

   Проверено: PHP-тесты страницы перехода, Python-тесты всех отказов,
   сквозной тест «пропуск от настоящего Laravel → Django на PostgreSQL»
   (`tests/test_bridge_parity.py`) и прогон в браузере через Apache:
   вход в Filament → пункт меню → раздел Django → выход.

   Ограничения, принятые сознательно: выход из админки Laravel не
   закрывает вход в Django (он истечёт сам, не позже чем через два
   часа, или «Выйти» на странице Django); пропуск в пределах своей
   минуты технически можно предъявить дважды — хранить погашенные
   пропуски Django негде, и это закрывают POST, `Cache-Control: no-store`
   и `Referrer-Policy: no-referrer`. Пункт меню пока видит только
   суперадмин: разделов на Django ещё нет.

   По дороге предохранитель записи сработал там, где и должен: сквозной
   тест пытался заблокировать пользователя из процесса Django и получил
   отказ — `users` Django может писать только внутри команды `admin`.
3. **Журнал действий** (раздел 5.1): каждое изменение из админки Django
   пишется в `admin_actions` так же, как пишет `AuditObserver`.
4. **Первая таблица — страны** (`countries`, `country_translations`):
   раздел админки на Django, перенос правил `Country` (раздел 5) и
   сидера `GeoSeeder`, который скрипт запуска гоняет на каждом деплое;
   сверка с PHP; затем раздел в Filament убирается, таблица переходит
   в `OWNED_TABLES`. Отдельно проверить кэши Laravel, где лежат списки
   стран: после записи из Django они не должны показывать старое.
5. Остальные 19 таблиц этапа — тем же путём, по одной-две за раз.

### Этап 3. Публичные страницы, только чтение (6–8 недель)

Каталог, визитки, новости, статические страницы. Записи в базу нет,
сессия только читается.

**Здесь первая настоящая трудность — общая сессия.** Сейчас
`SESSION_DRIVER=database`, то есть обе стороны могут читать одну таблицу
`sessions`. Но Laravel хранит содержимое как base64 от PHP-сериализации
и подписывает куку своим `APP_KEY`. Django нужен переходник, который
читает этот формат.

Порядок:
1. Сначала Django только **читает** сессию (узнать, кто вошёл).
2. Запись сессии остаётся за Laravel до этапа 5.
3. Заложить на один переходник отдельные две недели и отдельный тест:
   «вошёл на странице Laravel → перешёл на страницу Django → остался
   тем же пользователем».

Не начинать этап 3, пока это не работает на тестовом стенде.

### Этап 4. Каталог (10–12 недель)

Самая посещаемая часть. Переносить по одной странице, каждую держать
неделю под наблюдением, прежде чем браться за следующую.

### Этап 5. Кабинет (10–12 недель)

Вход, регистрация, профиль компании, чаты, отзывы. Здесь Django
становится хозяином сессии и таблицы `users`.

Пароли: в `User` стоит приведение `'password' => 'hashed'`, отдельного
`config/hashing.php` в проекте нет — значит работает умолчание Laravel,
то есть bcrypt. Django bcrypt понимает: достаточно поставить
`BCryptPasswordHasher` первым в `PASSWORD_HASHERS`. **Перехешировать
пароли не нужно и нельзя** — исходных мы не знаем. Проверить на копии
боевой базы **до** этапа, а не во время: взять десяток строк
`users.password` и убедиться, что Django принимает те же пароли.

Самый большой кусок — 14 604 строки. Зато целиком за `/admin`

Прокси больше никуда не смотрит. Django становится хозяином схемы:
`managed = True`, история миграций Laravel переносится в Django одним

**Итого: 58–76 недель.** Это полтора года для команды, которая занята

### Неделя 2. `savdex:uzum-ping` ✅

секреты, запись в лог. Платёж не проводится.

Знакомство с тем, как приложение берёт настройки и секреты, — на задаче,
где ошибка видна сразу и стоит ноль.

Сделано. Два намеренных расхождения, оба описаны в заголовке
`python/savdex/payments/uzum.py`: код ошибки едет полем исключения,
а не выковыривается регулярным выражением из собственной русской
фразы; пароль прокси маскируется до последнего «@», а не до первого.
Третье отличие не намеренное, а вынужденное: внутри скобок стоит текст
самого драйвера, и у cURL он не такой, как у httpx. Классификация

Заодно добавлена ветка, которой у PHP-версии нет: кириллица в ключе
(русская «с» вместо латинской «c» при копировании из документа) роняла
бы команду `UnicodeEncodeError` вместо объяснения.

### Недели 3–4. `savdex:export-xlsx` ✅

Выгрузка книг Excel. Читает почти всю базу, пишет файлы на диск.

Самая содержательная из безопасных: связи между таблицами, форматы,

двумя реализациями, лист за листом.

Сделано. Описание 16 листов и 235 столбцов сгенерировано из
PHP-исходника, а не перепечатано, и тест следит, чтобы оно не
разошлось с PHP-версией. Книги обеих реализаций совпадают ячейка
в ячейку — вместе с типами, шириной столбцов, закреплённой шапкой
и фильтром — на базе, наполненной крайними случаями: JSON
в разных видах, текст длиннее предела ячейки, ведущие нули,
удалённые записи.

Сравнение живёт в CI: при любой правке Python-выгрузки, PHP-выгрузки
или миграций схема строится миграциями Laravel, база наполняется,
обе команды выгружают, книги сверяются.

### Работа на боевом сервере: тень

Выгрузку делают регулярно, поэтому Python-версия поставлена на боевой
сервер сразу — но сначала в тени PHP-версии, а не вместо неё
(как её потом переключили — ниже).

Кнопка «Выгрузить сейчас» в админке (раздел «Система → Выгрузка в
Excel») ставит выгрузку в очередь. Воркер делает её PHP-версией, затем
Python-версия выгружает те же данные рядом и сверяет книги ячейка
в ячейку. Скачивается PHP-файл, итог сверки виден в списке выгрузок.
Сбой, расхождение или таймаут Python выгрузку не роняют — файлы уже
готовы. Это и есть финальная сверка на боевых данных, только без копии
базы и без риска.

Выгрузка отдаёт почту, телефоны и IP всех пользователей, поэтому
раздел прав отдельный («Выгрузка базы») и ни в одну роль не входит:
по умолчанию только суперадмин, остальным — поимённо. Запуск и каждое
скачивание пишутся в журнал действий. Файлы — на постоянном диске
(`storage/app/private/exports`), хранятся последние 10.

**Один снимок базы на обе версии.** Первые боевые выгрузки дали две
сверки «расходится» из пяти: «Тендеры, Просмотров: в базе 40, в файле
39». Книги были верны — посреди выгрузки кто-то открыл тендер, и
версии прочитали разные состояния базы. Теперь запуск открывает
в PostgreSQL транзакцию REPEATABLE READ, READ ONLY, берёт её снимок
(`pg_export_snapshot()`) и отдаёт его Python-версии (`--snapshot`):
обе версии и обе собственные сверки читают одно и то же состояние,
сколько бы посетителей ни было на сайте. Транзакция закрывается после
сверки на Python. Проверено тестом, который крутит счётчики
просмотров всё время выгрузки (`python/tests/test_export_parity.py`).
Урок на будущее: всё, что сравнивает две реализации на живой базе,
должно читать её одним снимком.

**Переключение на Python (сентябрь 2026).** После исправления снимка
пять боевых выгрузок подряд совпали с PHP, и основной стала
Python-версия (`EXPORTS_PRIMARY`, по умолчанию `python`). Порядок
теперь такой, из того же снимка базы: PHP-версия пишет свои книги
в `php/`, Python — на место скачиваемых и сверяет их с PHP-книгами.
Отдаётся Python-книга, только если она сошлась с базой (собственная
сверка); расхождение с PHP при этом видно в списке, как раньше было
видно расхождение Python с PHP. Если Python-выгрузка упала, не
уложилась во время или не сошлась с базой — на место скачиваемых
встают PHP-книги, и в списке это отмечено. Выгрузка из-за переезда
не пропадает.

Откат без деплоя кода: `EXPORTS_PRIMARY=php` в переменных Render —
и всё как до переключения. Старые выгрузки в истории скачиваются
по-прежнему.

**Когда удалять PHP-версию.** Когда ещё несколько выгрузок подряд
пройдут на Python с «совпала» и без отката на PHP-книги. Удаление —
отдельная правка: вместе с PHP-версией уходит и сверка, поэтому
перед ним стоит ещё раз прогнать сравнение в CI на свежем наполнении.

### Неделя 5. `savdex:admin` ✅

Выдача прав администратора. **Первая команда, которая пишет в базу.**

Пишет в `users`, а у `User` событий модели нет — то есть первая запись
делается туда, где скрытых правил заведомо нет. С этой недели Django
получает роль в PostgreSQL с правом записи, но **только на `users`**.

Сделано: `python/savdex/admins.py` и команда `manage.py admin`
с теми же параметрами, что у `php artisan savdex:admin`. Запись —
только внутри `allowed_writes("users")`: таблица по-прежнему Laravel,
Django получил узкое, заявленное в `guards.SHARED_WRITES` разрешение,
а не хозяйство (раздел 6 тут не срабатывает — Laravel в `users` пишет
и дальше).

**Сверка.** `python/tests/test_admin_parity.py` запускает обе команды
на одной базе на одиннадцати случаях — новый администратор, каждая
форма выбора роли, существующий пользователь с подтверждённой почтой
и без, удалённая учётка, неизвестная роль, кривая почта — и требует
одинаковых строк в `users`, одинаковых кодов возврата и одинаковых
сообщений. Отдельно Laravel сам проверяет пароль, выданный Python-версией,
той же проверкой, что при входе. `python/tests/test_admins.py` сверяет
с PHP правило проверки почты (на 45 трудных адресах), список ролей и
хеши.

**Что нашлось по дороге.**

- *Хеш `$2b$` PHP не узнаёт.* Библиотека bcrypt для Python пишет префикс
  `$2b$`, PHP — `$2y$`. Алгоритм один и тот же, но
  `password_get_info()` для `$2b$` отвечает «unknown», и Laravel при
  входе бросает исключение: администратор, заведённый Python-версией,
  не вошёл бы в админку вовсе. Строки в базе при этом выглядели бы
  правильно — поймала это только проверка пароля самим Laravel.
- *PHP-команда падала на удалённой учётке.* Поиск Eloquent удалённых
  не видит, а почта уникальна и среди них: команда пыталась завести
  второго пользователя и падала на уникальности с трассировкой.
  Исправлено в обеих половинах: теперь отказ с объяснением («учётка
  удалена такого-то числа, восстановите её в админке»). Молча
  восстанавливать удалённого и давать ему права нельзя — удаляли
  не просто так.
- *Строка «0» для PHP — ложь.* `--password=0` в PHP значит «сгенерировать»,
  `--role=0` — «роль по умолчанию». Повторено, чтобы одинаковый вызов
  давал одинаковый итог.
- *Ошибки Laravel печатает в обычный вывод*, Python-команды — в поток
  ошибок, как положено. Слова одинаковые; сверка сравнивает оба потока
  вместе.

**Роль в PostgreSQL для Django.** Предохранитель в коде — второй замок;
первый — права базы, их не обойти. Роль `savdex_django` читает всё,
а пишет только те столбцы `users`, которые пишет команда: удалить
пользователя, сменить ему компанию или тронуть другую таблицу она
не может. Проверено на PostgreSQL 16: команда работает, `check_postgres`
работает, `update users set company_id`, `delete from users` и запись
в `companies` получают «permission denied».

Как это сделано на Render — без psql (в образе его нет) и без
подстановок руками: блок ниже вставляется в Shell службы сайта
и выполняется через Laravel, от имени владельца базы. Имя базы и
владельца он берёт сам, пароль генерирует сам и печатает одной короткой
строкой. Повторный запуск безопасен: заменяет пароль, права не дублирует.

```bash
php artisan tinker --execute='
$db = DB::connection();
$pw = bin2hex(random_bytes(24));
$exists = $db->scalar("select count(*) from pg_roles where rolname = ?", ["savdex_django"]);
$db->statement(($exists ? "ALTER" : "CREATE")." ROLE savdex_django LOGIN PASSWORD ".$db->getPdo()->quote($pw));
$db->statement("GRANT CONNECT ON DATABASE \"".$db->getDatabaseName()."\" TO savdex_django");
$db->statement("GRANT USAGE ON SCHEMA public TO savdex_django");
$db->statement("GRANT SELECT ON ALL TABLES IN SCHEMA public TO savdex_django");
$db->statement("ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO savdex_django");
$db->statement("GRANT INSERT (name, email, is_admin, admin_role, status, password, must_change_password, email_verified_at, created_at, updated_at) ON users TO savdex_django");
$db->statement("GRANT UPDATE (is_admin, admin_role, status, password, must_change_password, email_verified_at, updated_at) ON users TO savdex_django");
$db->statement("GRANT USAGE ON SEQUENCE users_id_seq TO savdex_django");
echo PHP_EOL.$pw.PHP_EOL.PHP_EOL;
'
```

`ALTER DEFAULT PRIVILEGES` без `FOR ROLE` относится к тому, кто
выполняет, — то есть к владельцу, который потом и накатывает миграции
Laravel: новые таблицы сразу видны Django на чтение. Проверено на базе,
устроенной как на Render (владелец не суперпользователь, с CREATEROLE).

Затем в переменных службы на Render:
`DJANGO_DATABASE_URL` = `postgres://savdex_django:<пароль>@<хост>/<база>`.
Хост — тот же, что у Laravel; узнать его без пароля:

```bash
php artisan tinker --execute='echo parse_url(app(App\Support\DatabaseExports::class)->databaseUrl(), PHP_URL_HOST), PHP_EOL;'
```

Laravel эту переменную не читает, Python читает её первой. Выгрузка по
кнопке по-прежнему идёт под ролью Laravel: она передаёт Python адрес
явно, иначе не смогла бы разделить с ним снимок базы. Проверка —
`cd python && .venv/bin/python manage.py check_postgres`.

**Что выяснилось при настройке на сервере.** Длинную строку из Shell
Render не скопировать целиком: терминал переносит её, и в значение
попадают пробелы и переносы, а дефис на стыке строк теряется. Отсюда
блок печатает только пароль (48 символов — одна строка, выделяется
двойным щелчком), а остальное собирается по шаблону. Копирование — правой
кнопкой: Ctrl+Shift+C в Chrome открывает инструменты разработчика. И
ещё: без `APP_URL` в панели команда печатала `http://localhost/admin` —
PHP получает адрес из скрипта запуска (`RENDER_EXTERNAL_URL`), и
Python теперь идёт тем же путём.

Запуск на сервере (Shell на Render):

```bash
cd python && .venv/bin/python manage.py admin boss@savdex.uz --role=admin
```

PHP-команда остаётся рядом, пока Python-версией не выдадут права
несколько раз без замечаний; затем её можно удалить.
