# Переезд на PostgreSQL

Сайт работал на SQLite: файл `/var/data/database.sqlite` на постоянном диске
Render. Один файл — один писатель, а пишут в него трое: веб-сервер, планировщик
и воркер очереди. Под нагрузкой это «database is locked» и 500 там, где нужно
было подождать долю секунды. Серверная база снимает это ограничение, позволяет
снимать бэкапы и подключать отчёты (Metabase), чего файл на диске не позволял.

Код к переезду готов: драйвер `pdo_pgsql` собран в образе, entrypoint понимает
`DB_CONNECTION=pgsql`, все 57 миграций проверены на PostgreSQL 16, весь набор
тестов прогнан на нём же.

## Что уже сделано в репозитории

| Изменение | Зачем |
|---|---|
| `app/Console/Commands/CopyDatabase.php` | Перенос данных SQLite → PostgreSQL |
| `config/database.php`: `sqlite_source`, `pgsql_target` | Источник и приёмник переезда, не конфликтующие по `DB_URL` |
| `render.yaml`: блок `databases`, `TARGET_DB_URL` | База описана в Blueprint и создаётся до переключения |
| `app/Models/Wallet.php` | Списание условным UPDATE вместо `lockForUpdate` |

## Почему именно так

**Схему создают миграции проекта, а не конвертер.** Конвертер вроде pgloader
выводит типы из значений SQLite, где нет ни `boolean`, ни `json`: `is_active`
приехал бы числом, `tags` — текстом, и `where('is_active', true)` на PostgreSQL
упал бы с несовпадением типов. Поэтому сначала `migrate`, потом копирование
строк.

**Внешние ключи не отключаются.** У приложения на Render нет прав
суперпользователя, а `SET CONSTRAINTS ALL DEFERRED` молча не трогает
недеферрабельные ограничения Laravel. Вместо этого таблицы сортируются по
зависимостям, а связи, замкнутые в кольцо (`users.company_id` → `companies`,
`companies.verified_by` → `users`), вставляются пустыми и заполняются вторым
проходом.

**Счётчики последовательностей сбрасываются.** PostgreSQL ведёт их отдельно от
данных: после вставки строк с готовыми `id` счётчик остаётся на единице, и
первое же новое объявление упало бы с «duplicate key value violates unique
constraint».

**Переносятся не все таблицы.** `sessions`, `cache`, `cache_locks`, `jobs`,
`job_batches`, `failed_jobs`, `password_reset_tokens` — состояние работающего
процесса, а не данные площадки: люди просто войдут заново. `migrations`
заполняет `migrate` на приёмнике.

**Файлы не переезжают.** Логотипы, фото объявлений и документы лежат на диске
`/var/data/storage`. Диск остаётся смонтированным, удалять его нельзя.

## Порядок действий

### Этап 1. Создание базы

Изменения этой ветки должны попасть в ветку, которую читает Blueprint
(`claude/website-copy-new-design-xaxsr0`) — иначе Render продолжит видеть
прежний `render.yaml`, и базы не появится.

Дальше: **Blueprints → savdex → Sync**. Render создаст базу `savdex-db`
(тариф basic-256mb) и передаст сервису её адрес в `TARGET_DB_URL`.

Регион базы обязан совпадать с регионом веб-сервиса, иначе каждый запрос
получает лишние десятки миллисекунд.

**Сайт при этом не переключается.** Он продолжает работать на SQLite:
`DB_CONNECTION` не задан, `DB_DATABASE` по-прежнему указывает на файл. Это
намеренно — см. следующий этап.

### Этап 2. Перенос данных

Переключать сайт на пустую базу нельзя: между переключением и переносом
пройдут минуты, и всё, что посетители успеют за них создать — регистрации,
объявления, оплаты, — сотрёт перенос с `--truncate`. Поэтому данные
переезжают в уже созданную базу, пока сайт ещё живёт на SQLite.

Открыть Shell веб-сервиса в панели Render (или `render ssh savdex`):

```bash
php artisan migrate --database=pgsql_target --force
php artisan savdex:copy-database --truncate
```

Путь к источнику подставляется сам: подключение `sqlite_source` берёт его из
`DB_DATABASE`, то есть из той самой базы, на которой сейчас работает сайт.

`--truncate` обязателен, и без него команда откажется работать: часть миграций
наполняет таблицы сама (типы компаний, наборы кредитов, настройки), поэтому
свежий приёмник не пуст, и вставка поверх падала бы с «duplicate key» на
середине переноса.

До первой вставки команда проверяет источник на две вещи, которые SQLite не
контролирует, а PostgreSQL не прощает: строки длиннее объявленной колонки и
содержимое json-колонок. Обе проверки показывают сразу все найденные места
таблицей, а не первое из них — чинится всё за один заход.

Дальше команда печатает число строк по каждой таблице и в конце сверяет
источник с приёмником. Расхождение — отказ с ненулевым кодом возврата:
наполовину переехавшая база хуже, чем непереехавшая.

Ожидаемый хвост вывода:

```
Второй проход: восстановление кольцевых связей…
 companies.verified_by: 12

Сброс счётчиков последовательностей…
 последовательностей обновлено: 52

Перенесено строк: 574 в 22 таблицах. Число строк совпадает во всех таблицах.
```

### Этап 2а. Переключение сайта

Только теперь, на уже наполненной базе. В `render.yaml` заменить

```yaml
      - key: DB_DATABASE
        value: /var/data/database.sqlite
```

на

```yaml
      - key: DB_CONNECTION
        value: pgsql
      - key: DB_URL
        fromDatabase:
          name: savdex-db
          property: connectionString
```

и синхронизировать Blueprint ещё раз. `TARGET_DB_URL` после этого не нужен.

Записи, сделанные в SQLite между переносом и переключением, потеряются,
поэтому между этапами 2 и 2а не должно быть суток — выбирайте тихое время и
делайте их подряд. Если между ними прошло много времени, перенос достаточно
повторить: он идемпотентен.

### Этап 3. Проверка

Пройти по сайту:

- вход в кабинет и в админку `/admin`;
- каталог с поиском на кириллице и на латинице;
- карточка компании и раскрытие контакта — списывается ли кредит;
- создание нового объявления (проверяет сброс счётчиков);
- загрузка фото (проверяет, что диск на месте).

### Этап 4. После переезда

Файл `/var/data/database.sqlite` не удалять две недели: это единственный путь
отката. Откат — вернуть `DB_CONNECTION=sqlite` и `DB_DATABASE=/var/data/database.sqlite`
в Blueprint. Записи, сделанные в PostgreSQL после переключения, при откате
теряются, поэтому решение принимается в первые часы.

Дальше:

1. Проверить, что в панели базы включены ежедневные бэкапы.
2. Ограничить внешний доступ к базе списком адресов: **Database → Access
   Control**. По умолчанию Render открывает её всему интернету.
3. Завести пользователя только на чтение для отчётов:

   ```sql
   CREATE USER metabase WITH PASSWORD 'сюда-длинный-пароль';
   GRANT CONNECT ON DATABASE savdex TO metabase;
   GRANT USAGE ON SCHEMA public TO metabase;
   GRANT SELECT ON ALL TABLES IN SCHEMA public TO metabase;
   ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO metabase;

   -- Персональные данные и секреты: доступ забрать обратно
   REVOKE SELECT ON users, sessions, payment_methods FROM metabase;
   ```

4. Через две недели удалить файл SQLite с диска и убрать из entrypoint ветки
   для SQLite.

## Что стало возможным после переезда

Это уже не часть переезда, а следующий шаг:

- перевести колонки `json` в `jsonb` — компактнее, быстрее, индексируемо;
- заменить поиск по `LIKE '%…%'` на `pg_trgm` с GIN-индексом;
- вынести планировщик и воркер очереди в отдельный сервис Render;
- добавить CI с прогоном тестов на PostgreSQL — сейчас в репозитории нет
  ни одного workflow;
- перевести кэш и сессии из базы в Redis.

## Локальная проверка переезда

Повторить весь путь на своей машине, не трогая боевую базу:

```bash
# PostgreSQL в докере
docker run -d --name savdex-pg -e POSTGRES_PASSWORD=postgres \
  -p 5432:5432 postgres:16

export TARGET_DB_URL="pgsql://postgres:postgres@127.0.0.1:5432/savdex"
export SOURCE_DB_DATABASE="$PWD/database/database.sqlite"

php artisan migrate --database=pgsql_target --force
php artisan savdex:copy-database --truncate
```

Прогон тестов на PostgreSQL:

```bash
DB_CONNECTION=pgsql DB_URL="pgsql://postgres:postgres@127.0.0.1:5432/savdex_test" \
  php artisan test
```
