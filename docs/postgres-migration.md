# Переезд базы с Neon на PostgreSQL в Render

Площадка работает на PostgreSQL, но база живёт не в Render, а на **Neon** —
отдельном облачном сервисе, на бесплатном тарифе. Подключил её не нынешний
владелец, и обнаружилось это случайно, когда `savdex:check-postgres` показала,
что сайт и переменная `TARGET_DB_URL` смотрят в разные базы.

Две причины переехать:

- **Задержка.** Neon снаружи, и каждый запрос к базе уходит в интернет и
  возвращается. База Render стоит в одном регионе с сайтом (Oregon) и доступна
  по частной сети.
- **Бесплатный тариф Neon засыпает при простое.** Первый запрос после паузы
  идёт с заметной задержкой, и её видит посетитель.

## Что уже есть

| Что | Где |
|---|---|
| База в Render | `savdex-db`, Oregon, платный тариф, пустая |
| Адрес базы Render | переменная `TARGET_DB_URL` у сервиса |
| Адрес базы Neon | переменная `DB_URL` у сервиса, с ней работает сайт |
| Перенос со сверкой | `php artisan savdex:copy-database` |
| Проверка базы | `php artisan savdex:check-postgres` |

## Порядок действий

Всё выполняется в Shell сервиса `savdex`.

### 1. Схема на новой базе

```bash
php artisan migrate --database=pgsql_target --force
```

Схему создают миграции проекта, а не перенос: так в новой базе окажутся
настоящие типы колонок, а не угаданные по значениям.

### 2. Репетиция переноса

```bash
php artisan savdex:copy-database --from=pgsql --to=pgsql_target --truncate
```

`--from=pgsql` — это база, с которой сайт работает сейчас, то есть Neon.
`--to=pgsql_target` — новая база Render.

Команда печатает, между какими базами идёт перенос, и называет их по именам с
сервера, а не по именам переменных. Сверьте эту строку глазами, прежде чем
отвечать на что-либо дальше.

Перенос можно повторять сколько угодно: `--truncate` каждый раз очищает
приёмник. Репетиция нужна, чтобы увидеть проблемы до боевого захода.

### 3. Боевой перенос и переключение

Эти два шага идут подряд, в тихое время. Между ними сайт продолжает писать в
Neon, и всё записанное за этот промежуток потеряется.

```bash
php artisan savdex:copy-database --from=pgsql --to=pgsql_target --truncate
```

Дождитесь строки «Число строк совпадает во всех таблицах», затем в панели
Render замените у сервиса значение `DB_URL` на адрес базы Render, тот самый,
что лежит в `TARGET_DB_URL`. Сервис пересоберётся.

### 4. Проверка

```bash
php artisan savdex:check-postgres
```

Строка «Сайт и проверка» должна сказать, что обе смотрят в одну базу. Дальше
пройдите по сайту: вход в кабинет и в админку, каталог с поиском на кириллице и
на латинице, карточка компании, создание объявления, загрузка фото.

### 5. После переезда

Базу Neon не удалять две недели: это единственный путь отката. Откат — вернуть
прежний адрес в `DB_URL`.

Когда новая база отработает:

1. Проверить, что в панели Render включены бэкапы.
2. Оставить в Access Control только нужные адреса.
3. Завести пользователя только на чтение для отчётов.
4. Удалить базу Neon и переменную `TARGET_DB_URL`.

## Что перенос делает и чего не делает

**Не переносятся** `sessions`, `cache`, `cache_locks`, `jobs`, `job_batches`,
`failed_jobs`, `password_reset_tokens` — это состояние работающего процесса, а
не данные площадки: люди просто войдут заново. Таблицу `migrations` заполняет
`migrate` на приёмнике.

**Не переносятся файлы.** Логотипы, фото объявлений и документы лежат на диске
`/var/data/storage`. Диск остаётся смонтированным, удалять его нельзя.

**Порядок таблиц считается по внешним ключам.** Кольцо `users.company_id` ↔
`companies.verified_by` разрывается: колонка вставляется пустой и заполняется
вторым проходом. Кандидатом на разрыв может стать только таблица, чьи незакрытые
ссылки допускают NULL.

**Счётчики последовательностей сбрасываются.** Иначе первая же новая запись
упала бы с «duplicate key».

**Приёмник сверяется с источником** по числу строк в каждой таблице. Расхождение
— отказ с ненулевым кодом возврата.

## Защиты

Перенос отказывается работать, когда:

- источник и приёмник — одно подключение;
- в приёмнике нет схемы;
- в приёмнике уже есть строки, а `--truncate` не указан;
- в источнике есть значения длиннее колонки приёмника или битый JSON;
- **приёмник с `--truncate` оказался базой, с которой работает сайт.**

Последняя защита появилась после того, как выяснилось, что баз две. Сравниваются
не строки настроек, а ответы серверов: один сервер отвечает на десяток разных
адресов, а одна база называется по-разному в разных переменных. Перепутанные
местами источник и приёмник превратили бы перенос в удаление боевых данных.

## Локальная проверка

Повторить весь путь на своей машине, не трогая ничего боевого:

```bash
docker run -d --name pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:16
createdb -h 127.0.0.1 -U postgres source && createdb -h 127.0.0.1 -U postgres target

export DB_CONNECTION=pgsql
export DB_URL="pgsql://postgres:postgres@127.0.0.1:5432/source"
export TARGET_DB_URL="pgsql://postgres:postgres@127.0.0.1:5432/target"

php artisan migrate --force && php artisan db:seed --force
php artisan migrate --database=pgsql_target --force
php artisan savdex:copy-database --from=pgsql --to=pgsql_target --truncate
```
