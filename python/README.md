# Python-половина SavdEX

Каркас Django, с которого начинается перенос площадки с Laravel.
Зачем и в каком порядке — [docs/migration-to-python.md](../docs/migration-to-python.md).

Сейчас здесь каркас, предохранители и две перенесённые команды —
проверка базы и прозвон платёжного шлюза. Приложение отвечает
на один адрес: `/up`.

## Запустить у себя

Нужен [uv](https://docs.astral.sh/uv/) и Python 3.11 или новее.

```sh
cd python
uv sync --all-groups
uv run pytest -q          # 72 проверки, 9 пропустятся без PostgreSQL
uv run ruff check .
uv run mypy savdex
```

Базы для большинства проверок не нужно: они идут на SQLite в памяти.
Девять проверок требуют настоящего PostgreSQL — то, чего у SQLite нет:
версия сервера, права ролей, `has_table_privilege`. Есть база — укажите
её, и пропусков не останется:

```sh
SAVDEX_TEST_PG_URL=postgres://... uv run pytest -q   # 81 проверка
```

В CI такую базу поднимает служебный контейнер: пропущенная проверка —
не проверка.

Чтобы поднять само приложение, нужна та же база, с которой работает
Laravel, — через `DATABASE_URL` или через переменные `DB_HOST`,
`DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD` (те же имена,
что в `.env` у PHP; двух наборов имён для одной базы быть не должно).

```sh
DATABASE_URL=postgres://... uv run python manage.py runserver
```

## Что здесь лежит

| Файл | Зачем |
|---|---|
| `savdex/guards.py` | Предохранители переноса. **Самое важное здесь** |
| `savdex/apps.py` | Включает предохранители при старте. Без него они не работают |
| `savdex/settings.py` | Настройки. База, часовой пояс и хеш паролей взяты у Laravel |
| `savdex/checks.py` | Проверка базы — первая перенесённая команда |
| `savdex/payments/uzum.py` | Прозвон Uzum Checkout — вторая |
| `savdex/text.py` | Склонения: «1 таблица», «2 таблицы», «5 таблиц» |
| `savdex/urls.py` | Пока только `/up` |
| `conftest.py` | Подмена базы на SQLite для проверок |

## Проверка базы

Первая перенесённая команда — `savdex:check-postgres` из PHP
(неделя 1 этапа 1).

```sh
DATABASE_URL=postgres://... uv run python manage.py check_postgres
```

Отвечает тем же отчётом, что PHP-версия: доступность, версия, схема,
данные — со склонениями и подсказками теми же словами. Три вещи
намеренно расходятся, и почему — написано в заголовке
`savdex/checks.py`. Коротко: права проверяются наоборот (Django
не должен уметь писать) и вместо сверки двух баз показывается
последняя применённая миграция Laravel — по ней видно, живая база
перед нами или снимок недельной давности.

## Прозвон платёжного шлюза

```sh
uv run python manage.py uzum_ping
```

Спрашивает у Uzum статус несуществующего заказа и по ответу говорит,
где затык: сеть (адреса площадки нет в белом списке), ключи или
настройки. **Платёж не проводится, в базу ничего не пишется.**

Секреты в выводе закрыты — команду часто вставляют в задачу
и пересылают в переписке.

Два намеренных расхождения с PHP-версией описаны в заголовке
`savdex/payments/uzum.py`. Одно из них нашлось при переносе и было
исправлено **в обеих** половинах: маскировка адреса прокси обрывалась
на первом «@» и выпускала хвост пароля.

## Предохранители

`savdex/guards.py` закрепляет в коде два правила переноса, которые
иначе держались бы только на памяти людей.

**Запись в чужую таблицу отказывает.** Пока таблица принадлежит
Laravel, Django её только читает. Не договорённость, а обёртка вокруг
каждого запроса к базе: ловит и ORM, и `cursor.execute`.

Так это выглядит:

```
WriteToForeignTableError: Таблица «listings» принадлежит Laravel,
Django её только читает (правило 4.1 в docs/migration-to-python.md).
Если её хозяин действительно переходит — сначала перенесите правила
модели из раздела 5, потом добавьте таблицу в OWNED_TABLES.
```

Причина строгости — раздел 5 документа. Половина правил площадки живёт
в событиях моделей Eloquent: пересчёт рейтинга компании, запрет
возвращать отклонённое объявление на витрину, сброс устаревших
переводов у резюме. Код на Django, который пишет в те же таблицы
напрямую, обойдёт их **молча**. Ошибка проявится не сразу и не громко —
расхождением данных через месяц.

**Схему базы меняет только Laravel.** `manage.py migrate` не делает
ничего: маршрутизатор `LaravelOwnsSchema` запрещает миграции, а `CREATE`
и `ALTER` не проходят предохранитель. Все изменения структуры базы идут
через `database/migrations` у PHP — до самого конца переноса.

### Как передать таблицу Django

Одна строка в `OWNED_TABLES`, но перед ней — три условия:

1. Правила модели из раздела 5 документа перенесены;
2. На них написаны проверки pytest, и они **падают** без переноса;
3. Laravel в эту таблицу больше не пишет.

Порядок, в котором таблицы переходят, — раздел 6 документа.

Предохранитель — второй замок, а не первый. Первый — роль в PostgreSQL
без права записи, её выдаёт тот, кто настраивает Render. Код можно
обойти, права базы — нет. Есть ли она — покажет `check_postgres`,
строка «Запись».

### Почему предохранитель включается в apps.py

Получатель сигнала `connection_created` регистрируется при импорте
модуля, а импортировать его должен кто-то явно. В первой версии этого
не было: ссылки на `savdex.guards` в `DATABASE_ROUTERS` не хватает,
маршрутизатор Django создаёт лениво — уже после того, как соединение
открыто.

Предохранители при этом были украшением: в работающем приложении
запись в чужую таблицу доходила до базы. Все проверки проходили,
потому что тестовый файл импортирует модуль сам.

Отсюда `tests/test_guard_installed.py` — он запускает отдельный процесс
и смотрит, висит ли обёртка на соединении после обычного
`django.setup()`. Проверку, которая импортирует проверяемое сама,
такая ошибка обходит.

## Чего здесь намеренно нет

- **Приложений Django** `auth`, `sessions`, `contenttypes`. Каждому
  нужны свои таблицы, а таблицы здесь заводит Laravel. Появятся
  на этапах 5 и 6.
- **Моделей.** Их сгенерирует `manage.py inspectdb` по существующей
  базе, когда будет доступ к копии боевой. Писать руками то, что уже
  описано в 74 миграциях, незачем.
- **Кода площадки** сверх двух перенесённых команд. Следующая —
  недели 3–4, `savdex:export-xlsx`.
