# Python-половина SavdEX

Каркас Django, с которого начинается перенос площадки с Laravel.
Зачем и в каком порядке — [docs/migration-to-python.md](../docs/migration-to-python.md).

Сейчас здесь каркас, предохранители и три перенесённые команды —
проверка базы, прозвон платёжного шлюза и выгрузка в Excel.
Приложение отвечает на один адрес: `/up`.

## Запустить у себя

Нужен [uv](https://docs.astral.sh/uv/) и Python 3.11 или новее.

```sh
cd python
uv sync --all-groups
uv run pytest -q          # 72 проверки, 9 пропустятся без PostgreSQL
uv run ruff check .
uv run mypy savdex
```

Базы для большинства проверок не нужно: они идут на SQLite в памяти.
Девять проверок требуют настоящего PostgreSQL — то, чего у SQLite нет:
версия сервера, права ролей, `has_table_privilege`. Есть база — укажите
её, и пропусков не останется:

```sh
SAVDEX_TEST_PG_URL=postgres://.../savdex_test uv run pytest -q
```

**В имени базы обязательно «test»** — проверки стирают схему целиком
и в базу с другим именем не пойдут. Переменную окружения легко
перепутать, а цена ошибки — боевая база.

Сравнение выгрузок PHP и Python (`test_export_parity.py`) требует ещё
и PHP с установленными зависимостями Laravel:

```sh
composer install                                    # в корне репозитория
SAVDEX_PARITY_PG_URL=postgres://.../savdex_test uv run pytest -q
```

В CI такую базу поднимает служебный контейнер: пропущенная проверка —
не проверка.

Чтобы поднять само приложение, нужна та же база, с которой работает
Laravel, — через `DATABASE_URL` или через переменные `DB_HOST`,
`DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD` (те же имена,
что в `.env` у PHP; двух наборов имён для одной базы быть не должно).

```sh
DATABASE_URL=postgres://... uv run python manage.py runserver
```

## Проверка базы

Первая перенесённая команда — `savdex:check-postgres` из PHP
(неделя 1 этапа 1).

```sh
DATABASE_URL=postgres://... uv run python manage.py check_postgres
```

Отвечает тем же отчётом, что PHP-версия: доступность, версия, схема,
данные — со склонениями и подсказками теми же словами. Три вещи
намеренно расходятся, и почему — написано в заголовке
`savdex/checks.py`. Коротко: права проверяются наоборот (Django
не должен уметь писать) и вместо сверки двух баз показывается
последняя применённая миграция Laravel — по ней видно, живая база
перед нами или снимок недельной давности.

## Прозвон платёжного шлюза

```sh
uv run python manage.py uzum_ping
```

Спрашивает у Uzum статус несуществующего заказа и по ответу говорит,
где затык: сеть (адреса площадки нет в белом списке), ключи или
настройки. **Платёж не проводится, в базу ничего не пишется.**

Секреты в выводе закрыты — команду часто вставляют в задачу
и пересылают в переписке.

Два намеренных расхождения с PHP-версией описаны в заголовке
`savdex/payments/uzum.py`. Одно из них нашлось при переносе и было
исправлено **в обеих** половинах: маскировка адреса прокси обрывалась
на первом «@» и выпускала хвост пароля.

## Выгрузка в Excel

```sh
DATABASE_URL=postgres://... uv run python manage.py export_xlsx
```

Две книги — компании и объявления, 16 листов, со сверкой записанного
с базой. Совпадает с PHP-версией ячейка в ячейку, и это проверяется
в CI сравнением двух реализаций на одной базе.

Почему сравнение, а не только собственная сверка: собственная сверка
перечитывает базу тем же путём, каким писала, и ошибку этого пути
не видит. Так и было с полями JSON — подробности в заголовке
`savdex/export/workbooks.py`.

На боевом сервере Python-версия — основная: кнопка «Выгрузить сейчас»
в админке отдаёт её книги, а PHP-версия выгружает рядом из того же
снимка базы для сверки (упал Python — отдаются PHP-книги; откат —
`EXPORTS_PRIMARY=php`). Кнопка делает выгрузку обеими и сверяет книги
(`--compare-with`, `--json` и `--snapshot` у команды — для этого вызова;
`--snapshot` заставляет читать тот же снимок базы, что и PHP-версия,
иначе сайт успевает поменять счётчики между двумя чтениями). Сравнение —
в `savdex/export/compare.py`: рабочий код, а не только тест. Подробно —
в `docs/migration-to-python.md`, раздел про недели 3–4.

В образе Docker окружение собирается по `uv.lock` без пакетов разработки
в `python/.venv`; сборка и сквозной прогон внутри образа проверяются
в CI (`.github/workflows/docker.yml`).

Описание листов (`savdex/export/sheets.py`) сгенерировано из
PHP-исходника. Правите в одной половине — правьте и в другой:
тест `test_export.py` заметит расхождение.

## На сервере: за Apache

На Render Django работает в той же службе, что и Laravel: скрипт запуска
(`docker/render-entrypoint.sh`) поднимает gunicorn на `127.0.0.1:8001`
и перезапускает его, если тот упал. Снаружи до него не достучаться —
только через Apache, который передаёт Django пути из
`docker/apache-python.conf`, а всё остальное отдаёт Laravel.

Отдать Django новый адрес — добавить строку `ProxyPass` в этот файл и
завести путь в `savdex/urls.py` (Apache передаёт путь целиком, без
обрезки). Откат — убрать строку и передеплоить. Проверка в CI
(`.github/workflows/docker.yml`) запускает контейнер целиком и ходит
в Laravel и в Django через настоящий Apache.

Локально так же, без Apache:

```bash
uv run gunicorn savdex.wsgi --bind 127.0.0.1:8001
curl 127.0.0.1:8001/py/up        # ok
```

## Вход в админку Django

Разделы админки переезжают на Django по одному (этап 2). Входа своего
у Django нет: сотрудник входит в админку Laravel и открывает пункт
«Админка на Python» (`/admin/python`). Laravel (`App\Support\PythonBridge`)
выдаёт пропуск на минуту, подписанный ключом из `APP_KEY`, и форма
приносит его в `/py/login`. Django проверяет подпись, сам читает
пользователя и его права из базы и ставит свою куку на два часа.
На каждом запросе пользователь перечитывается — блокировка действует
сразу. Права — `savdex/access.py`, копия AdminAccess; правите матрицу
в PHP — правьте и здесь, `tests/test_access_parity.py` покажет разницу.

Без `APP_KEY` в окружении вход выключен (503): подпись ключом
разработчика подделал бы кто угодно.

## Разделы админки на Django

Раздел — модель Django (`managed = False`, таблицу по-прежнему заводит
Laravel) и класс админки от `SavdexModelAdmin` с разделом прав AdminAccess:

```python
@register(Country, section="catalogs")
class CountryAdmin(SavdexModelAdmin):
    laravel_model = "App\\Models\\Country"  # как запись называется в журнале Laravel
```

Права, журнал (`created` / `updated` с «было — стало» / `deleted`) и
русские заголовки даёт `SavdexModelAdmin`. Прежде чем раздел пишет в
таблицу, таблица должна перейти к Django (`guards.OWNED_TABLES`), а роли
`savdex_django` нужны права на запись — их выдаёт миграция Laravel.

## Выдача доступа в админку

```bash
uv run python manage.py admin boss@savdex.uz                  # суперадмин
uv run python manage.py admin fin@savdex.uz --role=finance --name="Финансы"
uv run python manage.py admin mod@savdex.uz --moderator
```

Перенос `php artisan savdex:admin`, параметры те же. Пароль генерируется
и показывается один раз; при первом входе Laravel попросит его сменить.

Первая команда, которая пишет в базу, — поэтому повторено буква в букву
то, что PHP делает молча (подробности в заголовке `savdex/admins.py`):
проверка почты тем же правилом, что `filter_var`, генерация пароля как
`Str::password`, хеш bcrypt с префиксом `$2y$` — хеш `$2b$`, который
пишет библиотека Python, PHP не узнаёт, и Laravel не пустил бы такого
администратора. Совпадение с PHP проверяют `tests/test_admins.py` и
`tests/test_admin_parity.py`: вторая запускает обе команды на одной базе
и спрашивает у самого Laravel, принимает ли он выданный пароль.

Пишет только в `users` и только внутри `allowed_writes("users")` — см.
«Предохранители». На сервере — под своей ролью в PostgreSQL
(`DJANGO_DATABASE_URL`), которой разрешено писать только нужные поля
`users`; SQL роли — в `docs/migration-to-python.md`, неделя 5.

## Предохранители

`savdex/guards.py` закрепляет в коде два правила переноса, которые
иначе держались бы только на памяти людей.

**Запись в чужую таблицу отказывает.** Пока таблица принадлежит
Laravel, Django её только читает. Не договорённость, а обёртка вокруг
каждого запроса к базе: ловит и ORM, и `cursor.execute`.

Так это выглядит:

```
WriteToForeignTableError: Таблица «listings» принадлежит Laravel,
Django её только читает (правило 4.1 в docs/migration-to-python.md).
Если её хозяин действительно переходит — сначала перенесите правила
модели из раздела 5, потом добавьте таблицу в OWNED_TABLES.
```

Причина строгости — раздел 5 документа. Половина правил площадки живёт
в событиях моделей Eloquent: пересчёт рейтинга компании, запрет
возвращать отклонённое объявление на витрину, сброс устаревших
переводов у резюме. Код на Django, который пишет в те же таблицы
напрямую, обойдёт их **молча**. Ошибка проявится не сразу и не громко —
расхождением данных через месяц.

**Схему базы меняет только Laravel.** `manage.py migrate` не делает
ничего: маршрутизатор `LaravelOwnsSchema` запрещает миграции, а `CREATE`
и `ALTER` не проходят предохранитель. Все изменения структуры базы идут
через `database/migrations` у PHP — до самого конца переноса.

**Узкое разрешение — не переход хозяина.** Иногда Django нужно писать
в таблицу, которой по-прежнему владеет Laravel: команда `admin` пишет
в `users`. Для этого таблица заявляется в `SHARED_WRITES` с объяснением,
почему это безопасно (у модели нет событий, PHP пишет те же поля тем же
простым путём), а запись идёт только внутри блока:

```python
with allowed_writes("users"):
    cursor.execute("update users set ...")
```

Вне блока, в соседнем потоке и для любой другой таблицы предохранитель
по-прежнему отказывает.

### Как передать таблицу Django

Одна строка в `OWNED_TABLES`, но перед ней — три условия:

1. Правила модели из раздела 5 документа перенесены;
2. На них написаны проверки pytest, и они **падают** без переноса;
3. Laravel в эту таблицу больше не пишет.

Порядок, в котором таблицы переходят, — раздел 6 документа.

Предохранитель — второй замок, а не первый. Первый — роль в PostgreSQL
без права записи, её выдаёт тот, кто настраивает Render. Код можно
обойти, права базы — нет. Есть ли она — покажет `check_postgres`,
строка «Запись».

### Почему предохранитель включается в apps.py

Получатель сигнала `connection_created` регистрируется при импорте
модуля, а импортировать его должен кто-то явно. В первой версии этого
не было: ссылки на `savdex.guards` в `DATABASE_ROUTERS` не хватает,
маршрутизатор Django создаёт лениво — уже после того, как соединение
открыто.

Предохранители при этом были украшением: в работающем приложении
запись в чужую таблицу доходила до базы. Все проверки проходили,
потому что тестовый файл импортирует модуль сам.

Отсюда `tests/test_guard_installed.py` — он запускает отдельный процесс
и смотрит, висит ли обёртка на соединении после обычного
`django.setup()`. Проверку, которая импортирует проверяемое сама,
такая ошибка обходит.

## Чего здесь намеренно нет

- **Приложений Django** `auth`, `sessions`, `contenttypes`. Каждому
  нужны свои таблицы, а таблицы здесь заводит Laravel. Появятся
  на этапах 5 и 6.
- **Моделей.** Их сгенерирует `manage.py inspectdb` по существующей
  базе, когда будет доступ к копии боевой. Писать руками то, что уже
  описано в 74 миграциях, незачем.
- **Кода площадки** сверх трёх перенесённых команд. Следующая —
  неделя 5, `savdex:admin`: первая команда, которая пишет в базу.
